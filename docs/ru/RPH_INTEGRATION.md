# Интеграция с RAGE Plugin Hook

> Русская версия. English: [../RPH_INTEGRATION.md](../RPH_INTEGRATION.md).

## Статус

| Возможность | Состояние |
| --- | --- |
| Обнаружение и сообщение версии | **Работает** |
| Публикация в манифест модов | **Работает** |
| Точки регистрации для авторов модов | **Работает** |
| Загрузка и работа моста под RPH | **Работает** |
| Внутрипроцессный канал к плагину, загруженному RPH | **Не работает в реальной игре** — см. ниже |
| Перечисление плагинов RPH, вживую из RPH | Написано, но недостижимо, пока канал сломан |
| Наблюдение состояния LSPDFR (см. [LSPDFR_INTEGRATION.md](LSPDFR_INTEGRATION.md)) | Написано, но недостижимо, пока канал сломан |
| Репликация внутреннего состояния произвольного плагина RPH | **Невозможна** — предел того, что предоставляет RPH |

Последняя строка — предел RPH. Вторая — наша, и большую часть жизни проекта она
числилась работающей.

### Канал не пересекает границу AppDomain

`InProcessChannel` встречается через `AppDomain.CurrentDomain.SetData`. RAGE Plugin Hook
загружает **каждый плагин в собственный AppDomain** — его лог сообщает об этом при
каждом запуске:

```
AppDomainPool::InitializeAppDomain: Creating new app domain "Gtamp.RphBridge_AppDomain"
```

Данные `AppDomain` принадлежат домену. Мост пишет в словарь своего домена, а клиент под
ScriptHookVDotNet читает другой: мост стартует, объявляет себя и опрашивает ящик, который
никто никогда не наполнит, а клиент десять секунд ждёт и сообщает, что мост не ответил.
Обе половины написаны правильно. Неправильна встреча между ними.

Все тесты это проходили, потому что набор запускает обе точки в **одном** AppDomain, где
`AppDomain.CurrentDomain` — один и тот же объект для обеих сторон. Это тот же вид дефекта,
который проект уже находил в стыке между `ModEnvironment` и хостом и между потоком
сущностей и снапшотом: две верные половины и непроверенный шов.

**Что нужно, чтобы закрыть:** примитив уровня процесса вместо доменного состояния —
memory-mapped file под именованным мьютексом, с тем же кадрированием и теми же правилами
ограниченной неблокирующей очереди. **Это не сделано**, и пока не сделано, состояние RPH и
LSPDFR остаётся на той машине, где возникло. Мультиплеера это не затрагивает: канал несёт
только состояние модов.

**Как отличить одно от другого.** `RagePluginHook.log` со строкой
`[GTAMP] RPH bridge started` и клиент, который всё равно говорит, что мост не ответил, —
это ограничение. Без этой строки это проблема установки, и лог называет какая именно.

## RPH не обязателен

Ядро мультиплеера хостится на ScriptHookVDotNet. Работают все три конфигурации:

- GTA V + мультиплеер
- GTA V + мультиплеер + RPH
- GTA V + мультиплеер + RPH + LSPDFR

У `Gtamp.Adapters.Rph.dll` **нет ссылки на RAGE Plugin Hook на этапе
компиляции** — после фазы 7 он не называет ни одного типа `Rage`. Его проверка
`IsAvailable` читает только запись об обнаруженных модах, поэтому клиент без
установленного RPH безвредно загружает файл адаптера и сообщает, что тот
неактивен.

## Техническая проблема, сказанная прямо

RPH и ScriptHookVDotNet — два отдельных хоста, загружающих .NET-код в один и тот
же процесс GTA V. Поддерживаемого пути между ними нет.

- RPH предоставляет свой API сборкам, которые загружает **он сам**, а не
  произвольному коду в процессе.
- Работа RPH выполняется на собственном планировщике `GameFiber`. Обращаться к
  типам `Rage` из потока скриптов ScriptHookVDotNet небезопасно, даже когда сборка
  разрешается, потому что объекты RPH предполагают привязку к файберу.
- Публичного реестра загруженных плагинов RPH, доступного извне RPH, не
  существует.

**Слой:** изоляция хостов внутри процесса игры. Не игровой движок, не сеть —
граница между двумя .NET-хостами плагинов.

## Рассмотренные варианты

| Вариант | Вердикт |
| --- | --- |
| Рефлексия во внутренности RPH из потока SHVDN | Отклонён. Небезопасен относительно `GameFiber` и привязывается к неверсионируемым внутренностям, меняющимся с каждым релизом RPH |
| Хостить весь клиент под RPH вместо SHVDN | Отклонён. Делает RPH обязательным, что противоречит требованию |
| Две сборки, по одной на хост, с общим внутрипроцессным каналом | **Выбрано** |
| Межпроцессное взаимодействие (именованный канал) между ними | Отклонён. Процесс один, поэтому общий канал строго проще и с меньшей задержкой |

## Устройство, как оно построено

```
Процесс GTA V
├── ScriptHookVDotNet
│    └── Gtamp.Client.Shv           ← здесь живёт ядро мультиплеера
│         ├── Gtamp.Adapters.Rph    ← сторона ядра канала
│         └── Gtamp.Adapters.Lspdfr ← сторона ядра, темы LSPDFR
│                 ▲
│                 │  внутрипроцессный канал: байты под именем темы
│                 │  ограниченный, неблокирующий, без вызовов между планировщиками
│                 ▼
└── RAGE Plugin Hook
     └── Gtamp.RphBridge.dll        ← плагин RPH, работает на GameFiber
          легально использует API Rage, наблюдает LSPDFR через рефлексию
```

### Точка встречи

`Gtamp.Shared.Interop.InProcessChannel` — это шов. Два хоста в одном процессе
могут загрузить **разные копии одной и той же сборки**, и тогда тип из одного не
является тем же типом для другого, а любой общий объект нельзя привести. Поэтому
канал разделяет только типы фреймворка:

- `AppDomain.CurrentDomain.GetData/SetData`, хранящие `ConcurrentQueue<byte[]>`;
- `string.Intern` по фиксированному ключу как единственный объект блокировки,
  который обе стороны могут назвать, не договариваясь о типе;
- собственный кадр `[u8 version][u16 topicLength][topic utf8][payload]`, потому
  что гарантированно совпадает только байтовая раскладка.

Обе очереди **ограничены и неблокирующие**. Ни одна сторона не имеет права
блокировать другую: работа RPH идёт на `GameFiber`, а работа ядра — на потоке
скриптов, и блокирующий вызов из одного в другой приводит к взаимной блокировке
игры. Переполненная очередь выбрасывает самое старое сообщение и считает его в
`InProcessEndpoint.Dropped` — теряется свежесть, а не кадр.

### Раздача

Сообщения с одного канала нужны двум адаптерам: RPH нужны рукопожатие и список
плагинов, LSPDFR — события состояния. `InProcessChannel.OpenCoreSide()` возвращает
представление на *одну* пару очередей, а не приватную, поэтому два адаптера,
вычитывающие её каждый сам по себе, крали бы сообщения друг у друга.
`Gtamp.Client.Mods.BridgeLink` владеет конечной точкой и раздаёт сообщения по
темам; адаптеры подписываются и никогда не трогают конечную точку напрямую.
Исключения обработчиков считаются, а не пробрасываются, чтобы один сломанный
адаптер не остановил сообщения, которых ждёт другой.

### Темы

| Тема | Направление | Полезная нагрузка |
| --- | --- | --- |
| `gtamp.describe` | ядро → мост | пусто; «расскажи всё, что видишь» |
| `gtamp.hello` | мост → ядро | `state=running;bridge=…;rph=…;lspdfr=…` либо `state=stopped` |
| `gtamp.rph.plugins` | мост → ядро | `Имя\|Версия;Имя\|Версия;…` |
| `gtamp.lspdfr.event` | мост → ядро | `key=value;key=value` — только то, что изменилось |
| `gtamp.mod.payload` | в любую сторону | непрозрачные байты, принадлежащие моду |

**Цена, которую это создаёт:** состояние RPH пересекает очередь, а не читается
напрямую, поэтому оно по построению устарело на один интервал опроса (50 мс на
стороне моста), и каждому куску состояния, достойному репликации, нужен явный
кодировщик на стороне моста. Альтернативой была потоконебезопасная рефлексия во
внутренности, которая работала бы в демонстрации и отказала бы в поле.

## Что делает мост

`src/Gtamp.RphBridge` — обычный плагин RPH: `[assembly: Plugin(...)]`, `Main()` на
`GameFiber`, `Finally()` при выключении.

1. Открывает сторону плагина канала и объявляет себя со своей версией, версией
   RPH и версией LSPDFR, если она есть.
2. Каждые 5 секунд перечисляет сборки, загруженные RPH, и сообщает имя и версию
   из `PluginAttribute` каждой. Этот атрибут — **публичная поверхность**, а не
   внутренность RPH, поэтому такой подход безопасен между релизами RPH.
3. Каждые 50 мс опрашивает LSPDFR через `LspdfrObserver` и публикует изменения.
4. Отвечает на `gtamp.describe` полной картиной, чтобы клиент, подключившийся
   позже, не остался только с теми изменениями, которые пропустил.
5. При выключении отправляет `state=stopped`, чтобы ядро перестало сообщать
   устаревшее состояние, а не ждало тайм-аута.

Если мост не отвечает в течение 10 секунд, адаптер RPH сообщает об этом на уровне
предупреждения и называет обе причины: игра запущена не через RPH либо моста нет
в папке `Plugins` RPH.

## Предел, который не является пунктом дорожной карты

**RPH не даёт плагину способа перечислить объекты другого плагина или управлять
ими.** Нет реестра сущностей другого плагина, нет шины событий, нет интерфейса
состояния. Значит, читать в общем виде нечего: «реплицировать плагины RPH» — не та
функция, которую можно построить извне этих плагинов.

**Теперь это проверено, а не предположено.** Вся публичная поверхность
`RagePluginHookSDK.dll` перечислена по метаданным сборки, и единственные связанные
с плагинами члены — это `Rage.Attributes.PluginAttribute` (метаданные сборки,
описывающие *ваш собственный* плагин) и `Rage.Game.ReloadActivePlugin`,
`TerminateActivePlugin`, `UnloadActivePlugin`, каждый из которых действует на
активный плагин, то есть на ваш. Нет ни `GetPlugins`, ни реестра плагинов, ни
какого-либо межплагинного аксессора. Раньше это ограничение утверждалось по
документации; теперь оно утверждается по сборке.

Для контраста стоит отметить: **у LSPDFR такой метод есть** —
`Functions.GetAllUserPlugins()`, возвращающий сборки, которые загрузил сам LSPDFR.
Он перечисляет плагины LSPDFR, а не RPH, и возвращает сборки, а не состояние, —
то есть определяет, что установлено (это уже покрывает манифест модов), и
по-прежнему ничего не говорит о том, что эти плагины делают.

Что возможно и реализовано:

- *факт* загрузки плагина, с его именем и версией, опубликованный в манифест
  модов, чтобы сервер и другие игроки могли его видеть;
- конкретно LSPDFR, потому что он публикует документированную поверхность
  `API.Functions`;
- всё, что плагин решит отправить сам, через `rph.event`.

## Авторам плагинов RPH

Зарегистрируйте сетевое событие через Mod SDK и отправляйте свои полезные
нагрузки:

```csharp
sdk.RegisterNetworkEvent("mymod.pursuit", (senderPlayerId, payload) => { /* применить */ });
sdk.SendNetworkEvent("mymod.pursuit", Serialize(pursuit));
```

Чтобы это событие дошло до *других игроков*, а не только до сервера, его имя
должно быть в серверном списке `relayedModEvents` (см.
[MOD_SDK.md](MOD_SDK.md#пересылаемые-события)). Сервер пересылает байты дословно,
не интерпретируя их, поэтому пересланное событие **не несёт серверного
авторитета** — это один клиент сообщает что-то другим. Всё, за что нужно
поручительство, требует серверного обработчика или RPC.

## Установка моста

`tools/package-client.sh` (или `.bat`) кладёт его в
`dist/client/RagePluginHook-plugins/`. Скопируйте содержимое этой папки в
`GTA V/Plugins/`. Без него адаптеры RPH и LSPDFR всё равно загружаются и всё равно
сообщают, что установлено; у них просто нет живого состояния, о котором можно
сообщить.

## Что здесь не проверено

Мост собирается против `RagePluginHook` 1.124.0, и его половина канала покрыта
тестами. **Он ни разу не запускался внутри настоящего процесса GTA V с
загруженным RPH** — для этого нужны Windows, лицензионная копия GTA V и сам RPH,
ничего из чего нет на машине, где всё это собиралось. Проверить удалось:
кадрирование, ограниченные очереди, раздачу по темам, изоляцию обработчиков,
рукопожатие, разбор списка плагинов и его попадание в манифест, тайм-аут при
отсутствии ответа моста, а также сквозной путь изменения состояния LSPDFR до
другого игрока. Непроверенным остаётся поведение собственного загрузчика RPH и
тайминги `GameFiber`.
