# Система сущностей

> Русская версия. English: [../ENTITY_SYSTEM.md](../ENTITY_SYSTEM.md).

## Цель

Добавление нового вида сетевой вещи — фреймворком или модом — не должно требовать
трогать сетевой слой. Это требование, а тест, который его доказывает, —
`ModSdkTests.AModDefinedEntityReplicatesThroughTheOrdinarySnapshotPath`: сущность
«турель», определённая целиком в тестовом проекте, реплицирует полное состояние и
дельты по обычному пути снапшотов, без изменений где-либо ещё.

## Базовое состояние

Каждая сущность, встроенная или определённая модом, несёт:

| Поле | Назначение |
| --- | --- |
| `Id` | Назначается сервером, никогда не переиспользуется |
| `Type` | Идентификатор типа на проводе; ≥128 — диапазон модов |
| `OwnerId` | Игрок, который её симулирует; 0 = сервер |
| `Position`, `Velocity`, `Heading` | Трансформация |
| `Dimension` | Разделение инстансов; разные измерения никогда не видят друг друга |
| `InteriorId` | Интерьер GTA V, 0 — снаружи |
| `NetworkVersion` | Инкрементируется при каждой принятой мутации |
| `LastUpdateTick` | Тик сервера последней мутации |
| `CustomData` | Свободная строковая карта, принадлежащая модам |

`CustomData` намеренно `string → string`. Сервер, который никогда не слышал о
моде, всё равно может хранить, реплицировать и сохранять состояние этого мода на
каждой сущности дословно. Именно это позволяет миру мода пережить перезапуск на
чистой сборке сервера.

### Идентификаторы сущностей никогда не переиспользуются

Идентификатор обозначает одну сущность на всё время жизни сервера, а
`ReserveEntityIdsUpTo` при старте восстанавливает аллокатор за наибольший
сохранённый id. Поэтому устаревшая ссылка разрешается в «её нет», а не в другую
сущность, которой достался тот же номер, — это класс ошибок, который крайне трудно
диагностировать по симптомам. Покрывается
`PersistenceTests.EntityIdsAreNeverReusedAfterARestart`.

## Объявление типа

Поля объявляются, а не сериализуются вручную. Каждое объявление задаёт проверку
изменения, писателя и читателя:

```csharp
public sealed class TurretSerializer : EntitySerializer<TurretEntity>
{
    public TurretSerializer() : base(typeId: 128, typeName: "mod.turret") { }

    public override NetEntity Create(EntityId id) => new TurretEntity(id);

    protected override void DeclareFields(EntityFieldSet<TurretEntity> fields)
    {
        fields
            .Add("Ammo",
                 (a, b) => a.Ammo != b.Ammo,
                 (w, e) => w.WriteVarInt(e.Ammo),
                 (r, e) => e.Ammo = r.ReadVarInt())
            .Add("Deployed",
                 (a, b) => a.Deployed != b.Deployed,
                 (w, e) => w.WriteBool(e.Deployed),
                 (r, e) => e.Deployed = r.ReadBool());
    }
}
```

Базовые поля выше добавляются автоматически и всегда занимают одни и те же
битовые индексы во всех типах — именно это позволяет инспектору сущностей
оставаться универсальным.

- **Полное состояние** пишет каждое поле в порядке объявления.
- **Дельта** пишет varint-битовую маску, а затем только изменившиеся поля.
- **Неизменившиеся** сущности дают однобайтовую нулевую маску и вообще
  пропускаются писателем снапшотов.

Предел — 64 реплицируемых поля на тип. Сверх этого группируйте состояние в
`CustomData` или отдельную сущность: одна сущность с 64 полями — запах проекта, а
неограниченная маска стоила бы байтов на каждой дельте.

### Проверки изменения, а не равенство

Каждое поле само решает, что значит «изменилось». `Heading` использует эпсилон
0,0001°, переход погоды — 0,004 (один шаг квантования). Это важно: число с
плавающей точкой, отличающееся только ниже собственной точности на проводе, иначе
пересылалось бы вечно, сжигая бюджет на разницу, которую получатель не может
представить.

## Идентификаторы типов

| Диапазон | Владелец |
| --- | --- |
| 0 | Неизвестно/недопустимо |
| 1–127 | Встроенные: Player, Vehicle, Ped, Object, Weapon, Projectile, Pickup, Door, Mission, Marker |
| 128–255 | Определяемые модами, через `IModSdk.RegisterEntity` |

`ModSdk.RegisterEntity` отказывает идентификатору внутри встроенного диапазона
(`ModSdkTests.ModEntityIdsMustStayInTheReservedRange`) и отказывает любой
регистрации после запуска сетевого слоя: таблица типов, меняющаяся посреди сессии,
рассинхронизировала бы каждого клиента, который её уже согласовал.

## Хеш схемы

`EntityRegistry.ComputeSchemaHash` — это FNV-1a по отсортированной таблице типов:
каждый идентификатор типа, имя типа и имя поля. Клиент и сервер обмениваются им в
рукопожатии.

Несовпадение означает, что стороны расходятся в раскладке полей, и оно сообщается
как несовместимость модов при входе — а не обнаруживается позже как испорченный
снапшот, где незамеченное расхождение раскладки иначе и всплывает.

## Что реализовано сегодня

**`PlayerEntity`** полон для фаз 1 и 2: id игрока, имя, модель, здоровье,
максимальное здоровье, броня, флаги движения (присед, спринт, прыжок, падение,
плавание, ныряние, лазание, рэгдолл, смерть, прицеливание, стрельба,
перезарядка, ближний бой, в транспорте, посадка в транспорт, парашют, укрытие,
неуязвимость), состояние локомоции, текущее оружие, боезапас, точка прицеливания,
транспорт и место, уровень розыска, хеш анимации, измерение и интерьер.

Компоненты одежды и аксессуары добавлены в фазе 2. `PedAppearance` несёт двенадцать
слотов компонентов (drawable, texture, palette) и восемь слотов аксессуаров,
закодированных за масками присутствия, поэтому стандартный персонаж стоит три
байта вместо 46, которых потребовала бы фиксированная раскладка. Это одно
реплицируемое поле, записываемое целиком, потому что внешность меняется при
появлении и при смене одежды, а не покадрово.

### Каждый флаг позы и то, что его действительно применяет

Восемнадцать флагов снимаются с локального игрока и реплицируются. Это не то же
самое, что восемнадцать *используемых* флагов, и разница — ровно тот тип разрыва,
который прячется весь проект: состояние едет, хранится и печатается правильно и не
доходит до педа. Поэтому весь набор перечислен — применяется он или нет.

| Флаг | Кем применяется | Примечания |
| --- | --- | --- |
| `Dead` | `RemotePedController` → `DriveDead` | Ставится, а не задаётся задачей; дальше владеет анимация смерти |
| `Ragdoll` | `DriveRagdoll` + `RagdollDriver` | Голова и обе стопы корректируются импульсами |
| `InVehicle` | `SeatRemotePedInVehicle`, один раз на смену места | Ставится в сообщённую позицию только тогда, когда в локальной игре нет такого транспорта, чтобы сесть |
| `Aiming` | `TASK_AIM_GUN_AT_COORD` | Настоящая точка прицеливания с камеры стрелка |
| `Shooting` | Ретрансляция `WeaponShot` | Сами выстрелы, посчитанные по обойме |
| `Reloading` | `TASK_RELOAD_WEAPON`, один раз на перезарядку | Переиздание каждый кадр заставляет педа вечно ронять магазин |
| `Crouching` | `SET_PED_STEALTH_MOVEMENT` | В GTA V у педа нет приседания; то, что игрок видит как присед, — stealth-передвижение |
| `Sprinting` | — | Перекрыт `MovementState`, который уже используется при выборе походки. Флаг оставлен: он может понадобиться моду |
| `Jumping`, `Climbing` | **не применяются** | Оба — переходы длиной в секунду-две. Пока флаг доедет, игрок их закончил, а `TASK_JUMP` на педе, которого ведут к координате, дерётся с уже идущей задачей |
| `Falling` | **не применяется** | Локальный пед падает сам, когда под ним ничего нет. Принуждение задвоилось бы с собственной физикой игры |
| `Swimming`, `Diving` | **не применяются** | Пед, которому задали задачу в воде, плывёт сам. Не хватает *ныряния* — для него нужен набор подводных задач, это работа фазы 9 |
| `Melee` | **не применяется** | Задаче ближнего боя нужна цель-сущность, а цель не реплицируется — только флаг. Без цели пед машет в воздух в случайную сторону |
| `InCover` | **не применяется** | Укрытие — это позиция в мире, а не состояние педа. `TASK_STAY_IN_COVER` нужна точка укрытия, которую принимающий клиент должен найти сам, а неверная догадка прижмёт педа не к той стене |
| `Parachuting` | **не применяется** | Нужны проп парашюта, свой набор задач и автомат состояний купола. Запланировано вместе с общей работой по анимациям |
| `EnteringVehicle` | **не применяется** | Пед сажается напрямую; анимация посадки не проигрывается, поэтому игрок появляется в машине, а не залезает в неё |
| `Invincible` | только на сервере | Читается античитом как признак god mode. К удалённому педу не применяется никогда — он и так неуязвим, потому что его здоровье приходит с сервера |

Шесть применяются, один перекрыт, один серверный, десять не применяются. Эти
десять — реальный пробел, и он назван как пробел; каждый в списке потому, что
применить его плохо заметно хуже, чем не применять, а не потому, что о нём забыли.

### Поза рэгдолла

Флаг рэгдолла говорит, что тело падает. Он не говорит, где тело окажется, а это
другой вопрос: физические солверы недетерминированы между машинами, поэтому две
копии, получившие одно и то же начальное состояние, расходятся за несколько
кадров. Игрок, упавший лицом в стену на своём экране, лежит на спине посреди
дороги на всех остальных. Репликация одной позиции корня это не чинит, а прячет:
корень успевает, а всё, что к нему прикреплено, находится совсем не там.

`RagdollPose` несёт три позиции костей — голова, правая стопа, левая стопа — как
смещения от корня персонажа и только пока установлен флаг рэгдолла.
`RagdollDriver` превращает их в импульсы Euphoria, пропорциональные ошибке между
сообщённой позицией и локальной.

Четыре решения, которые стоит назвать, потому что каждое чего-то стоит:

- **Три кости, а не скелет.** У педа больше восьмидесяти костей; все они стоили бы
  на одного падающего игрока больше, чем весь остальной протокол вместе взятый.
  Голова и стопы фиксируют оба конца тела — то, что позиция корня выразить не
  может. Цена: руки, позвоночник и поворот головы не реплицируются вообще, они
  такие, какими их сделал локальный солвер.
- **Импульсы, а не установка позиции.** Запись позиций костей в работающий солвер
  — именно то, от чего реплицированные рэгдоллы дёргаются: на следующем шаге
  солвер выводит их заново из своих ограничений. Импульс оставляет управление
  ему. Цена: поза — это приближение, а не состояние. Конечность, зажатую
  геометрией, сквозь неё не протащить, а клиент с большим RTT видит тело, которое
  отстаёт и подтягивается, а не совпадает кадр в кадр.
- **Смещения, а не мировые позиции.** Дешевле на проводе (±8 м с шагом 7,8 мм
  вместо ±16 км с шагом 2 мм) и остаются верными, когда корень на принимающей
  стороне был интерполирован или скорректирован. Мировая позиция кости вместе с
  уехавшим корнем описывает разорванное тело.
- **Задержка на устаканивание и дистанция сдачи.** Первые десять кадров падения
  отдаются локальному солверу: имеющаяся поза описывает тело возрастом в один
  round trip, и тянуть за конечности в момент удара — получить падение, не похожее
  ни на одну из машин. Дальше восьми метров ошибки по корню две копии описывают
  уже разные падения, и пед ставится на место напрямую — один заметный телепорт
  против тела, которое иначе осталось бы не на той улице, пока не встанет.

Приём — тот же, к которому пришёл [RAGECOOP-V](https://github.com/RAGECOOP/RAGECOOP-V)
(MIT). Реализация, константы и обе оговорки выше — наши, код не копировался. Как и
всё в этом слое, решение покрыто юнит-тестами и **визуально в игре не проверено**.

Остальные пункты раздела 9 мастер-промпта — полный инвентарь, задачи сценариев —
**отсутствуют**. Они запланированы в [ROADMAP.md](ROADMAP.md), а не заглушены
пустыми значениями, потому что поле, которое ничего не реплицирует, хуже
отсутствующего: оно выглядит поддержанным.

**`CharacterEntity`** несёт всё, что есть общего у игрока и сетевого NPC — тело,
оружие, место в транспорте, внешность, — объявленное один раз в `CharacterFields`.
Две поддерживаемые вручную копии пятнадцати объявлений полей разошлись бы, а
расхождение между ними — это тихая порча декодирования, а не ошибка компиляции.

**`VehicleEntity`** несёт 27 реплицируемых полей. Некоторые намеренно сгруппированы:
шесть индексов окраски как одно поле `Colors`, ливрея и тип колёс как `Styling`,
текст и тип номера как `Plate`, обороты и передача как `Drivetrain`. На практике
они выставляются вместе, и каждое отдельное поле стоило бы бита маски и
собственного присутствия в каждой дельте, затрагивающей любое из них. Девятнадцать
булевых свойств транспорта — одно битовое поле `VehicleFlags` по той же причине:
три байта varint вместо девятнадцати полей.

Двери и шины упаковывают по два состояния на индекс в одно 16-битное слово: биты
0-7 — открыто или лопнуло, биты 8-15 — сломано или пробито.

**`PedEntity`** добавляет флаги поведения, уровень тревоги, хеши задачи и сценария,
цель в бою, группу отношений и свободный идентификатор группы, чтобы мод мог
держать набор педов вместе, не изобретая собственный реестр.

**Его поля поведения реплицируются и не применяются.** `Behaviour`, `AlertLevel`,
`TaskHash`, `ScenarioHash`, `CombatTargetId`, `RelationshipGroupHash` и `GroupId`
едут по проводу, и в игровом слое их никто не читает. Это не спрятанный недосмотр:
*решения* NPC принадлежат серверу, а у сервера нет ИИ, который бы их производил, —
применять пока нечего. Они перечислены здесь, а не оставлены выглядеть
поддержанными: поле, которое ничего не описывает, хуже отсутствующего — то же
правило, по которому живут зарезервированные идентификаторы типов.

`RemoteEntityManager` создаёт и ведёт педа для каждого из них — тем же
`RemotePedController`, что и педа игрока: выбор походки, пороги коррекции, поза
рэгдолла и обработка смерти — это одна и та же задача, а вторая копия этой логики
была бы вторым набором багов. Одно отличие, и оно намеренное: NPC с отсутствующей
моделью **подменяется**, потому что NPC — это декорация с ролью, а толпа с дырой
хуже толпы в чужой куртке. Игрок не подменяется никогда — нужно уметь узнать, на
кого смотришь.

Пока этого не было, тип регистрировался, сериализовался, дельта-кодировался,
сохранялся, реплицировался и принимался арбитром урона — и ни один клиент ничего
для него не создавал. Заспавненный NPC появлялся в состоянии мира и во всех
диагностиках и был невидим в игре.

**`ObjectEntity`** добавляет модель, поворот, здоровье, флаги и прикрепление к
другой сущности.
