# Сохранение состояния

> Русская версия. English: [../PERSISTENCE.md](../PERSISTENCE.md).

## Модель

```
СОСТОЯНИЕ МИРА НА СЕРВЕРЕ  →  СЛОЙ ХРАНЕНИЯ  →  SQLite
```

Сохранение происходит по таймеру (`saveIntervalSeconds`, по умолчанию 60), при
отключении игрока, по консольной команде `save` и при чистом выключении.

Загрузка происходит один раз при старте, до того как слушатель начнёт кого-либо
принимать.

## Хранилище

По умолчанию SQLite (`data/world.db`, режим WAL). Схема не использует
специфичных для SQLite типов, и каждый запрос — обычный параметризованный SQL,
поэтому переход на PostgreSQL — это смена драйвера, а не перепроектирование.

### Таблицы

| Таблица | Статус | Содержимое |
| --- | --- | --- |
| `players` | **Живая** | Токен личности, имя, позиция, здоровье, броня, модель, уровень розыска, измерение, интерьер, роль, деньги, последнее появление |
| `world_state` | **Живая** | Часы, погода, отключение света, наибольший id сущности, хеш схемы сущностей, метка времени сохранения |
| `entities` | **Живая** | Непрозрачные блобы полного состояния по id сущности и id типа |
| `vehicles`, `peds`, `objects` | Созданы, заполняются в фазах 3/5 | |
| `missions` | Создана, заполняется в фазе 6 | |
| `inventories` | Создана, заполняется в фазе 3 | |
| `mod_state` | Создана, заполняется в фазе 6 | Состояние «ключ/значение» в области мода, не привязанное к сущности |
| `permissions` | Создана, заполняется в фазе 10 | |
| `server_settings` | Создана, заполняется в фазе 10 | |

Таблицы поздних фаз создаются уже сейчас, чтобы базе, созданной ранней сборкой, не
понадобилась миграция, когда эти фазы придут.

## Непрозрачные блобы сущностей

Неигровые сущности хранятся как вывод писателя полного состояния их собственного
сериализатора, вместе с id типа. Слой хранения никогда их не интерпретирует.

Именно это позволяет **сущности, определённой модом, пережить перезапуск на
сервере, который ничего не знает об этом моде на уровне компиляции**. Блоб
уходит и возвращается; сериализатор, который его понимает, предоставляет мод при
загрузке.

Столбец `world_state.schema_hash` это охраняет. Если сохранённый хеш не совпадает
со схемой сущностей работающей сборки, значит раскладки полей изменились и блобам
доверять нельзя: записи игроков всё равно восстанавливаются, сохранённые блобы
сущностей пропускаются, а предупреждение называет оба хеша. Молча неверно
истолковать блоб было бы куда хуже, чем его потерять.

## Личность

Игроки идентифицируются по `IdentityToken` — GUID, сгенерированному при первом
запуске и сохранённому в клиентском `client.ini`.

Следствия, о которых стоит сказать явно:

- **Это не система аккаунтов.** Кто скопировал токен — тот и этот игрок.
  Настоящая аутентификация — фаза 10.
- **Не привязано к имени.** Игрок может свободно переименоваться и сохранить
  персонажа.
- **Не привязано к IP.** Переподключение с другого адреса работает.

## Перезапуск

```
СТАРТ СЕРВЕРА
  → открыть базу
  → загрузить world_state    часы, погода, наибольший id сущности
  → зарезервировать id сущностей   чтобы id никогда не переиспользовались
  → загрузить блобы сущностей      когда хеш схемы совпадает
  → принимать подключения
```

```
ВЫКЛЮЧЕНИЕ (Ctrl+C или команда `stop`)
  → уведомить подключённых игроков
  → сохранить каждого подключённого игрока
  → сохранить состояние мира
  → закрыть базу
```

`PersistenceTests.APlayerGetsTheirCharacterBackAfterAServerRestart` проходит весь
этот цикл: подключиться, походить, получить урон, погасить сервер, запустить новый
против того же файла, переподключиться с той же личностью и убедиться, что позиция,
здоровье, броня и мировые часы вернулись.

## Как это отключить

`"persistenceEnabled": false` в `server.json` подставляет
`NullPersistenceStore`. Каждый вызов становится пустышкой, и мир свеж при каждом
старте. Полезно для тестовых серверов; путь кода идентичен, так что больше ничего
не меняется.

## Запись идёт вне тик-потока

`BackgroundPersistenceStore` оборачивает настоящее хранилище и ставит записи в
очередь к рабочему потоку. Сохранение — это запись на диск, а запись на диск в
потоке симуляции — это заминка, которую чувствует каждый игрок; особенно теперь,
когда сохраняются и сущности, что делает сохранение транзакцией по всем объектам
мира.

Записи в очереди **склеиваются**: сохраняется только новейшее состояние для
каждого игрока, для мира и для набора сущностей. Поэтому медленный диск стоит
свежести, а не неограниченной очереди — а именно неограниченная очередь
превращает медленный диск в падение по нехватке памяти.

Две детали, которые важны:

- **Чтения видят записи в очереди.** Игрок, который сразу переподключился,
  получает своё последнее сохранение, даже если оно ещё в очереди, а не более
  старую копию с диска.
- **Выключение опустошает очередь.** Выключение, потерявшее последнее сохранение,
  — это как раз то, из-за чего чистый перезапуск всё равно теряет прогресс сессии.

Сами чтения остаются синхронными. Они происходят при старте и при входе — оба
случая достаточно редки, чтобы несколько миллисекунд не имели значения, — а
асинхронное чтение означало бы, что на вход нельзя ответить в том же тике, в
котором он получен.

## Миграции

Версия схемы живёт в базе, в таблице `schema_version`, и миграции выполняются по
порядку при открытии.

Версия хранится, а не выводится из того, какие таблицы существуют. Вывод работает,
пока два изменения не затронут одну таблицу, а затем молча делает не то.

Открытие базы, записанной **более новой** сборкой, отклоняется, а не делается на
удачу: понижение потеряло бы столбцы, добавленные новой сборкой.

## Известные пределы

- **Резервных копий нет.** Копируйте `data/world.db` сами. Поскольку включён
  режим WAL, копируйте рядом `-wal` и `-shm` или сначала остановите сервер.
- **Драйвера PostgreSQL пока нет.** SQL уже переносим — нет специфичных для
  SQLite типов, каждый запрос параметризован, — так что это смена драйвера, а не
  перепроектирование.
