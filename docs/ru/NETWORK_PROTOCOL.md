# Сетевой протокол

> Русская версия. English: [../NETWORK_PROTOCOL.md](../NETWORK_PROTOCOL.md).

Транспорт: UDP. Порядок байтов: little-endian. Версия протокола: **10**
(`ProtocolConstants.ProtocolVersion`); несовпадение отклоняется во время
рукопожатия с читаемым сообщением.

## Кадрирование пакетов

Каждая датаграмма начинается с магического числа `0x504D5447` (`"GTMP"`) и байта
вида. Магия — дешёвый фильтр, чтобы посторонний трафик отбрасывался до разбора.

### Без соединения (kind = 0)

Используется до существования сессии и только для рукопожатия.

```
u32      magic
u8       kind = 0
u8       messageType
varuint  length
bytes    payload
```

### Сессионный (kind = 1)

```
u32      magic
u8       kind = 1
u32      sessionId
u16      sequence        номер этого пакета; 1..65535, никогда не 0
u16      ack             наибольший номер пакета, полученный от собеседника, либо 0
u32      ackBits         битовое поле: бит i подтверждает (ack - 1 - i)
message* до конца датаграммы
```

Кадрирование сообщения внутри пакета:

```
u8       flags           бит0 = надёжное
u16      reliableSeq     присутствует только для надёжных
u8       messageType
varuint  length
bytes    payload
```

`MaxPacketSize` равен 1200 байт — достаточно мало, чтобы пережить наименьший MTU в
публичном интернете без IP-фрагментации. Одно сообщение может нести не более
`MaxPacketSize - 32` байт; всё, что больше, отклоняется на вызове отправки, а не
молча обрезается, и предполагается, что верхние слои сами делят свои полезные
нагрузки (кодировщик снапшотов так и делает).

## Надёжность

Подтверждение — **на уровне пакетов**. Каждый отправленный пакет запоминает, какие
идентификаторы надёжных сообщений он нёс; когда пакет подтверждён, все надёжные
сообщения внутри него списываются разом. Неподтверждённый пакет ставит в очередь
ровно свои собственные сообщения.

- **Тайм-аут перепосылки** использует оценщик Джекобсона/Карелса — тот же, что и
  TCP, — ограниченный диапазоном [50 мс, 1 с].
- **Упорядоченная доставка**: получатель буферизует надёжные сообщения,
  пришедшие не по порядку, и выдаёт их по порядку. Буфер ограничен 512 записями,
  чтобы враждебный собеседник не мог исчерпать память, придерживая один номер.
- **Подавление дубликатов**: надёжное сообщение с номером ниже отметки доставки
  отбрасывается. Поэтому перепосылки, пересекающиеся со своим подтверждением,
  бесплатны.
- **Учёт потерь**: пакет, выпавший из окна подтверждения в 32 пакета так и не
  будучи подтверждённым, засчитывается потерянным ровно один раз. Именно эту
  цифру показывает сетевой отладчик.

### Номер пакета 0 зарезервирован

Удалённый номер у собеседника начинается с нуля, поэтому его самому первому пакету
нечего подтверждать. Отправка `ack = 0` в этом пакете, при том что 0 — тоже
допустимый номер пакета, означает, что другая сторона прочтёт это как
подтверждение своего собственного первого пакета.

Это не косметика. Надёжные сообщения «подтверждённого» пакета списываются из
списка перепосылки и больше никогда не отправляются; а поскольку доставка
упорядочена, каждое последующее надёжное сообщение встаёт в очередь за номером,
который никогда не придёт, и канал заклинивает — молча, навсегда, до конца
соединения. Ситуация, которая это вызывает, совершенно обыденна: сервер ставит в
очередь уведомление о входе в тот момент, когда принимает клиента, ещё до того как
у клиента появится peer, чтобы его принять, а первое обновление состояния клиента
приносит обратно `ack = 0` до срабатывания таймера перепосылки.

Поэтому номера пакетов начинаются с 1 и пропускают 0 при переполнении, а `ack = 0`
означает «я от вас ещё ничего не получил» и не подтверждает ничего. Цена — один
бит подтверждения на каждые 65536 пакетов, что проявляется как одна лишняя
перепосылка.

Регрессионный тест:
`ReliabilityTests.AReliableMessageSentBeforeThePeerExistsIsStillDelivered`.

### Задержка подтверждения

Подтверждение ждёт до `NetPeer.MaxAckDelay` (20 мс) исходящего трафика, чтобы
поехать на нём попутчиком. Обе стороны обычно отправляют несколько раз в секунду,
поэтому подтверждения едут бесплатно; задержка порождает отдельный пакет только
когда собеседник иначе молчит.

Без этого собеседник, которому нечего отправлять, придерживает подтверждения до
секундного keep-alive, что раздувает измеренный RTT на порядок и задерживает
каждое решение о перепосылке. Это была реальная ошибка, пойманная тестом
`ReliabilityTests.RoundTripTimeIsEstimatedFromAcknowledgements`.

## Рукопожатие

```
КЛИЕНТ                                          СЕРВЕР
  │  ConnectRequest (без соединения)              │
  │  ─ версия протокола, версия клиента           │
  │  ─ имя игрока, токен личности, пароль         │
  │  ─ nonce клиента                              │
  │  ─ манифест модов + хеш схемы сущностей       │
  │ ────────────────────────────────────────────► │
  │                                               │ проверка версии
  │                                               │ проверка имени, пароля
  │                                               │ сравнение манифестов модов
  │                                               │ восстановление/создание игрока
  │  ConnectAccept (без соединения)               │
  │  ─ id сессии, id игрока, id сущности игрока   │
  │  ─ эхо nonce, частоты тика/снапшотов          │
  │  ─ время сервера, отчёт совместимости модов   │
  │ ◄──────────────────────────────────────────── │
  │                                               │
  │  ═════ дальше идут сессионные пакеты ═════    │
  │  ClientStateUpdate ──────────────────────────►│  30 Гц, ненадёжно
  │ ◄────────────────────────────────── Snapshot  │  20 Гц, ненадёжно
```

Когда сервер требует аутентификации — а это умолчание, — в середину добавляются
ещё две ноги:

```
  │  ConnectRequest ────────────────────────────► │
  │                                               │ проверка бана, затем случайный nonce
  │                                               │ и свежая пара ключей ECDH P-256
  │ ◄──────────── ConnectChallenge                │
  │  ─ serverNonce, имя сервера                   │
  │  ─ эфемерный ключ сервера (64 байта)          │
  │                                               │
  │  подпись(clientNonce ‖ serverNonce            │
  │           ‖ имя ‖ оба эфемерных ключа)        │
  │  ConnectProof ──────────────────────────────► │ проверка против заявленного ключа
  │  ─ публичный ключ личности, подпись           │ затем ECDH → общий секрет
  │  ─ эфемерный ключ клиента (64 байта)          │
  │ ◄──────────── ConnectAccept                   │
```

**Оба эфемерных публичных ключа входят в подписываемые байты.** Одна подпись,
доказывающая владение ключом личности, тем самым связывает и обмен ключами:
атакующий, подменивший любой из эфемерных ключей, ломает подпись, а не тихо
оказывается посередине сессии. Именно поэтому challenge несёт эфемерный ключ
сервера, а не досылает его позже — клиент обязан иметь его до того, как подпишет.

Запрос повторяется каждые 500 мс, до 32 попыток — поднято с 20, потому что четырём
ногам без соединения нужно два круговых прохода там, где двум хватало одного.

**Каждая нога идемпотентна, и иначе нельзя.** На потерянный challenge отвечают
повторной выдачей *того же самого* nonce для того же клиентского nonce: новый
обесценил бы доказательство, уже находящееся в пути, и сказал бы законному игроку,
что его ключ неверен. Потерянное доказательство переотправляет таймер повтора
клиента — который шлёт именно доказательство, а не начинает рукопожатие заново,
чтобы не выбросить дошедший challenge. Потерянный accept переотправляется, когда
доказательство приходит снова; именно поэтому путь доказательства тоже умеет
ответить сохранённым accept, как и путь запроса.

**Рукопожатие идемпотентно.** Accept — единственный пакет, за которым нет слоя
надёжности: он отправляется до того, как сессия существует. Если он потерян,
клиент повторяет запрос, и сервер обязан ответить на этот повтор, а не
маршрутизировать его в полуоткрытую сессию, созданную первым запросом. Повторный
запрос с тем же токеном личности и nonce получает байт-в-байт тот же accept
заново. Без этого клиент, чей accept потерялся, оказывается брошенным, пока не
сдастся; см. `SessionTests.ALostAcceptDoesNotStrandTheClient`.

Nonce также не даёт принять запоздавший accept от брошенной попытки за живую
сессию.

## Шифрование сессии

Как только доказательство проверено, обе стороны держат один и тот же общий
секрет ECDH, и сессия шифруется начиная с первого же сессионного пакета.
`encryptSessions` в `server.json` включён по умолчанию; выключение даёт сессию
открытым текстом, и сервер прямо пишет об этом в лог, а не деградирует молча.

Конструкция — **encrypt-then-MAC**: AES-256-CBC для конфиденциальности,
HMAC-SHA256, усечённый до 16 байт, для аутентичности, на независимых ключах.

```
                    общий секрет ECDH P-256
                               │
       ┌──────────┬────────────┼────────────┬──────────┐
   шифр c2s   MAC c2s      шифр s2c      MAC s2c    ключ IV
```

Пять ключей, каждый — `HMAC-SHA256(секрет, метка ‖ счётчик)` со своей парой
метка/счётчик (`gtamp-c2s-v1`, `gtamp-s2c-v1`, `gtamp-iv-v1`). Раздельные
направления означают, что перехваченный пакет клиента нельзя воспроизвести
обратно клиенту, а отдельный MAC-ключ означает, что ключ шифра никогда не
работает ещё и как MAC-ключ. Первая редакция `Derive` считала один и тот же HMAC
дважды и сделала бы ключ шифра равным MAC-ключу — эту ошибку стоит назвать
вслух, потому что снаружи не сломалось бы ничего наблюдаемого.

Шифрованный сессионный пакет оставляет заголовок открытым и запечатывает всё
после него:

```
u32      magic            ┐
u8       kind = 1         │
u32      sessionId        ├─ открытый заголовок — аутентифицирован, не зашифрован
u16      sequence         │
u16      ack              │
u32      ackBits          ┘
bytes    шифротекст         AES-256-CBC по всему блоку сообщений
16 байт  тег                HMAC-SHA256(macKey, заголовок ‖ шифротекст)[0..16]
```

**Заголовок остаётся читаемым намеренно.** Слою надёжности нужны поля номера и
подтверждения, чтобы маршрутизировать пакет ещё до того, как можно вывести IV, а
демультиплексору нужен id сессии, чтобы понять, какие ключи пробовать. Читаемый
не значит незащищённый: эти байты входят в MAC, поэтому переписывание номера
пакета делает пакет невалидным, а не перенаправляет перехваченный пакет в другое
место потока.

**IV выводится, а не передаётся.** Это один блок AES-ECB по байту направления и
номеру пакета на ключе IV. Так экономятся 16 байт в каждом пакете, и рассинхрона
из-за потерь быть не может — приёмник уже знает номер из заголовка. Накладные
расходы на пакет — 16 байт тега плюс дополнение CBC, и учёт `MaxPacketSize`
вычитает их *до* того, как сообщение допускается в пакет: включение шифрования
никогда не выталкивает за MTU пакет, который в него помещался.

**Пакет, не прошедший аутентификацию, отбрасывается целиком** и считается, а не
разбирается частично; ровно ради этого MAC и существует. Расшифровка возвращает
false, а не бросает исключение: подделанный или повреждённый пакет в публичной
сети — обычное событие, а не исключительное.

### Что это защищает, а что нет

| Защищено | Не защищено |
| --- | --- |
| Содержимое сообщений от пассивного слушателя на проводе | Анализ трафика — размеры и тайминги пакетов видны |
| Подмена любого байта, включая поля заголовка | Ноги рукопожатия без соединения, открытые по построению |
| Человек посередине без приватного ключа личности клиента | Оператор сервера, который законно держит ключи сессии |
| Повтор пакета в обратном направлении | Что угодно на уже скомпрометированной локально машине |

Прямую секретность (forward secrecy) дают эфемерные пары ключей: они создаются
на каждое соединение и уничтожаются вместе с сессией, поэтому добытый позже
приватный ключ личности не расшифрует записанную сессию.

`EncryptionTests` это доказывает, а не декларирует. Тест закладывает
строку-канарейку в сообщение чата, следит за виртуальным проводом на предмет
именно этих байт и требует их отсутствия — в паре с контрольным тестом, который
выключает шифрование и требует, чтобы та же канарейка *находилась*. Без контроля
тест, который вообще не видит провода, проходил бы по неверной причине.

**Ограничение платформы, названное прямо.** `ECDiffieHellman` отсутствует в
`netstandard2.0`. Именно поэтому `Gtamp.Shared` собирается сразу под
`netstandard2.0;net48;net8.0`, а сборка `EphemeralKeyExchange` под
`netstandard2.0` бросает `PlatformNotSupportedException`, а не откатывается на
что-то более слабое. Хост, способный загрузить только сборку `netstandard2.0`,
вообще не откроет шифрованную сессию — он падает громко, а не работает молча
открытым текстом. Поставляемые клиент и сервер работают на `net48`, так что на
практике этот путь не достигается.

**Два идентификатора в этой таблице зарезервированы, и ни один не отправляется.**
Согласование модов происходит внутри рукопожатия, потому что его надо решить до
того, как клиента пустили, а не после: манифест едет в `ConnectRequest`, а отчёт о
совместимости — в `ConnectAccept`. Идентификаторы оставлены, потому что формат на
проводе резервирует их заранее, а перенумерация ради закрытия дыры ломает всех
клиентов, уже говорящих на нём, — и `NetMessageTypeTests` следит за классификацией,
так что идентификатор, который начнут отправлять, уронит сборку, пока таблицу не
поправят.

### ModEvent (`0x2A`)

```
string   name            маршрутизация по имени, а не по id в порядке регистрации
varuint  senderPlayerId  только сервер → клиент; 0 означает сам сервер
bytes    payload         непрозрачно; ни одна сторона его не интерпретирует
```

Маршрутизация по имени, а не по идентификатору, выданному в порядке регистрации,
сделана намеренно: два клиента, загрузившие свои моды в разном порядке, иначе
направляли бы события друг друга в неправильный обработчик; кроме того, это
снимает потолок на количество событий, которые мод может зарегистрировать.

`senderPlayerId` существует потому, что сервер может пересылать событие клиента
остальным игрокам (см. [MOD_SDK.md](MOD_SDK.md#пересылаемые-события)).
Пересланное событие, потерявшее источник, было бы бесполезно для чего угодно
персонального. На участке клиент → сервер поле игнорируется: отправитель — это
сессия, по которой пришёл пакет, а значение, присланное клиентом, ничего не стоит.

## Снапшоты

```
varuint  snapshotId          ненулевой, растущий для каждого клиента
varuint  baselineId          0 означает «полное состояние»
varuint  tick
f64      serverTime
varuint  ackClientUpdate     новейшее обновление клиента, учтённое этим снапшотом
u8       flags               бит0 = присутствует блок окружения
                             бит1 = получившийся view содержит весь мир
[environment]
varuint  removedCount
varuint  removedEntityId *
varuint  entityCount
  varuint  entityId
  u8       entryFlags        бит0 = полное состояние
  [u8      typeId]           только для полного состояния
  fields                     полное: все поля; дельта: varuint-маска + изменённые
```

Идентификаторы снапшотов — **на клиента**, а не глобальные: каждый клиент
подтверждает свой собственный поток, а сервер кодирует относительно того, что этот
клиент подтвердил последним.

### Почему базовые представления, а не один текущий мир

Дельту нужно декодировать ровно против того состояния, против которого она была
написана. Пока подтверждение летит, сервер продолжает кодировать против более
старого baseline, поэтому клиент не может просто применять дельты к одному
изменяемому миру — старый baseline должен всё ещё существовать.

Поэтому обе стороны хранят короткую историю неизменяемых `EntitySnapshotView` (по
умолчанию 64), и каждая дельта называет то представление, против которого была
написана. Применение дельты против неверного baseline **отвергается**, а не
делается на удачу: `SnapshotCodec.Apply` бросает исключение, и клиент запрашивает
ресинхронизацию.

Представления разделяют ссылки на сущности для всего, что не изменилось, поэтому
история глубиной 64 стоит одного словаря на снапшот, а не 64 глубоких копий
(`SnapshotTests.BaselineViewsShareUnchangedEntityInstances`).

Кольцо вытесняет старейшее первым, кроме одного слота: `SnapshotHistory.PinnedId`
держит baseline, против которого противоположная сторона пишет прямо сейчас, и
вытеснение через него перешагивает. Без этого клиент, который отстал, сам себе
ломает возможность догнать: сервер продолжает писать против последнего baseline,
подтверждение которого он слышал, клиент возвращается к очереди снапшотов,
написанных против этого baseline, и применение очереди сохраняет по view на
снапшот — так что после 64 из них baseline, который называет каждый оставшийся
снапшот, оказывается вытеснен теми самыми снапшотами, которые его называют.
Дальше — один resync и серия отброшенных снапшотов ровно такой длины, как
перебор. Клиент знает, какой view беречь, потому что каждый снапшот называет свой
baseline, — и закрепляет его до того, как искать
(`PartialSnapshotTests.TheBaselineTheServerIsStillWritingAgainstSurvivesACatchUpBurst`).

### Байтовый бюджет

У каждого снапшота есть жёсткий байтовый бюджет (`snapshotByteBudget`, по
умолчанию 1024). Кодировщик обходит сущности в порядке приоритета и пишет то, что
помещается. Всё, что не поместилось, **откладывается на следующий снапшот**, а не
теряется — его baseline-состояние просто переносится у клиента дальше.

Это и есть механизм, позволяющий оптимизировать репликацию, ни разу не сокращая
состояние мира на сервере.
`StressTests.DistanceNeverRemovesAnEntityFromTheServerWorld` разбрасывает 100
сущностей по всей карте, далеко за любым радиусом стриминга единственного
подключённого игрока, и утверждает, что клиент сходится ко всем ним.

### Отсутствие — это не удаление

«Baseline-состояние переносится дальше» верно для дельты, где пропущенная
сущность просто не упомянута. Для полного снапшота это **не** так: его baseline —
пустота, и сущность, не поместившаяся в полный снапшот, отсутствует во view,
который строит клиент. Клиент, читающий отсутствие как удаление, её уничтожит.

Бит1 во flags это закрывает. Писатель считает view, который в итоге получит
приёмник, против мира, который он этому приёмнику реплицирует, и ставит бит
только когда эти два совпадают. Удаление после этого — вывод, который клиенту
разрешено делать **только из снапшота, заявляющего весь мир**; из любого другого
пропавшая сущность — та, что ещё в пути. `EntitySnapshotView.IsComplete` несёт
тот же ответ на обеих сторонах.

Считается это против мира, а не берётся из «отложил ли этот пакет что-нибудь»,
потому что поместившаяся дельта не делает мир целым, если её baseline уже был
неполным — и, ровно так же, более поздний снапшот, закрывающий пробел, делает мир
целым снова.

Известное ограничение: отсутствие — единственный сигнал удаления, который несёт
view, поэтому сущность, удалённая сервером в том же снапшоте, где что-то было
отложено, задержится у клиента до следующего полного снапшота — обычно до
следующего кадра. Закрыть это значило бы носить явный список удалений рядом с
каждым view; это не сделано.

### Порядок, пока ничего не подтверждено

Приоритет обычно понижает сущность, как только она отправлена, чтобы следующий
снапшот начинался с той, что ждала дольше всех. Для дельт это правильно, а до
прихода первого подтверждения — нет, потому что тогда *каждый* снапшот полный и
написан против пустоты: снапшот 1 нёс бы одну половину мира, а снапшот 2 — тоже
написанный против пустоты, потому что подтверждение не успело дойти, — другую,
и каждый описывал бы мир, в котором другой половины нет. Подключающийся игрок
видел, как одни и те же припаркованные машины создаются и уничтожаются по разу
на снапшот, пока длится эта очередь.

Поэтому пока `AcknowledgedSnapshotId` равен 0, история отправок в оценку не
входит, и порядок — чистая функция от мира (`ReplicationPriority.Score`). Каждый
полный снапшот в такой очереди несёт тогда одни и те же сущности и просто
повторяет сам себя, пока один из них не дойдёт; после этого отложенные сущности
становятся наивысшим приоритетом и приходят дельтами.

Цена в том, что схождение теперь ждёт подтверждения, а не происходит само собой:
если бы терялись все подтверждения, сервер бесконечно повторял бы первый срез.
При 20 снапшотах в секунду для этого нужна почти полная потеря на пути
подтверждений, на которой раньше сработает таймаут самой сессии, — но это
реальная зависимость, а не теоретическая.

### Почему снапшот отражает номер обновления клиента

Каждое `ClientStateUpdate` несёт растущий `updateSequence`, а каждый снапшот
отражает новейший из них, который сервер успел обработать к моменту записи этого
снапшота.

Без этого клиент не может различить две ситуации, а реагировать на них надо
противоположно:

| Снапшот расходится с тем, что я сообщил, потому что… | Правильная реакция |
| --- | --- |
| сервер **отверг** это (античит, возрождение, удержание авторитета) | привязаться к серверу |
| сервер **ещё не видел** этого, когда писал снапшот | не делать ничего |

Принять второе за первое — это самонанесённый рубер-бэндинг, причём особенно
неприятный: клиент отскакивает к значению, которое сервер *уже принял*, затем
сообщает откатившееся значение, и изменение теряется навсегда. Эхо делает различие
точным — клиент держит короткую историю своих отчётов по номерам и судит каждый
снапшот по тому отчёту, на который этот снапшот отвечает.

Регрессионный тест:
`CorrectionTests.AnAcceptedChangeIsNotUndoneByASnapshotThatPredatesIt`.

## Ориентация

Ориентация едет тремя углами — тангаж, крен и курс, — потому что именно это отдаёт
и принимает игра, и круговой обход точен. Формат на проводе никогда не был
проблемой.

Проблемой была *независимая* интерполяция этих трёх. Тангаж, крен и рыскание — не
независимые оси: смешивая каждую по отдельности, проходишь через ориентации, не
лежащие ни на одном пути между концами. Машина, переворачивающаяся на крышу,
по дороге разворачивает нос, а сущность с тангажом около вертикали теряет ось
целиком — gimbal lock, пришедший в интерполятор, а не в формат.

`NetQuaternion.LerpEuler` переводит оба конца в кватернионы, сферически
интерполирует и переводит обратно. `FromEuler` и `ToEuler` — точные взаимно
обратные по построению, и это то свойство, которое важно: каждый конец выборки
бит-в-бит совпадает с тем, что сообщила игра, а любое расхождение с собственным
порядком осей движка ограничено кадрами строго между двумя выборками.

Педы сохраняют более дешёвое смешивание одного угла. У педа значима одна ось, и
нет тангажа с креном, с которыми её надо связывать.

## Выстрелы

Выстрел — это событие, а не состояние, поэтому он не едет в снапшоте. Флаг
стрельбы в `PlayerFlags` говорит, что оружие стреляет; он не может сказать, как
часто, а винтовка на 600 выстрелов в минуту держит его шесть кадров на выстрел
при 60 fps. Патроны считаются по обойме — она убывает ровно на один за выстрел, —
и каждый уходит отдельным `WeaponShot`.

Ненадёжно в обе стороны, намеренно: вспышка, доехавшая после того, как её пуля уже
арбитрирована, хуже, чем отсутствующая.

Три вещи сервер на веру не принимает:

| Заявление | Что делает сервер |
| --- | --- |
| Кто стрелял | Перезаписывается из сессии. Клиент, называющий стрелка сам, может назвать чужого. |
| Где был ствол | Отбрасывается, если дальше `GameServer.MaxMuzzleOffset` (10 м) от собственной позиции стрелка. |
| Как часто | Token bucket, `ShotBudget`: 80 выстрелов в секунду устойчиво, 20 в запасе. Сверх бюджета выстрелы отбрасываются и **не** считаются нарушением — потолок всего вдвое выше минигана, и счёт нарушений там рано или поздно выкинул бы игрока за то, что у него миниган. |

Ретрансляция ограничена дистанцией `GameServer.ShotRelayRange` (250 м), считаемой
от *серверной* позиции стрелка. Это фильтр только репликации: ни одна сущность не
покидает мир ни на каком расстоянии, и
`WeaponShotTests.AShotFromTheOtherSideOfTheMapIsNotRelayed` проверяет и то и
другое — выстрел не нарисован, оба игрока в мире.

**Ретранслированная пуля не несёт урона и не будет.** Попадание арбитрируется из
`DamageReport` по собственному миру сервера; нарисованная пуля, которая ещё и
ранит, засчитала бы одно нажатие на спуск по разу на каждого клиента, который её
нарисовал. Принимающий клиент стреляет с уроном 0.

**Снаряды не отражаются.** Ракета или граната — это летящая сущность, и рисовать
её мгновенной линией от ствола до попадания значит показать всем взрыв, пришедший
со скоростью света. Группы оружия `Thrown` и `Heavy` исключены — вместе с
рельсотроном, hitscan-оружием в одной группе с ракетницей. Неправильно
нарисованная ракета — ошибка хуже.

## Квантование

| Величина | Кодирование | Диапазон | Худшая ошибка |
| --- | --- | --- | --- |
| Ось позиции | zig-zag varint от `round(value × 512)` | ±16384 м (XY), ±2048 м (Z) | 0,98 мм |
| Ось скорости | zig-zag varint от `round(value × 128)` | ±256 м/с | 3,9 мм/с |
| Угол | `u16` от `градусы × 65536/360` | 0–360° | 0,0027° |
| Единичный скаляр | `u8` | 0–1 | 0,2 % |
| Ось смещения кости | zig-zag varint от `round(value × 128)` | ±8 м | 3,9 мм |

Значения вне диапазона **ограничиваются, а не заворачиваются**: испорченная
координата даёт позицию на краю мира, которую ловит валидатор, а не позицию,
которая молча оказывается где-то правдоподобно.

Граница для позиции проверяется на 5000 случайных выборках в
`SerializationTests.QuantizedPositionStaysWithinTheDocumentedErrorBound`.

## Фрагментация

Надёжное сообщение, превышающее бюджет на сообщение, режется на фрагменты, каждый
из которых — обычное надёжное сообщение:

```
u16 groupId | u8 index | u8 count | u8 innerType | chunk
```

Порядок и перепосылка достаются бесплатно от надёжного канала, поэтому сборке не
нужна собственная схема подтверждений. Получатель буферизует фрагменты до полноты
набора, затем выдаёт собранное сообщение под его внутренним типом.

Пределы, оба — границы по памяти: 256 КБ на сообщение и 8 одновременных наборов
фрагментов. У собеседника, открывающего больше наборов, чем он завершает, самый
старый отбрасывается.

**Ненадёжная фрагментация не предлагается, а отклоняется.** Потеря любого одного
фрагмента теряет всё сообщение, поэтому эффективная частота потерь умножается на
число фрагментов: сообщение из 5 фрагментов на канале с 10 % потерь доходит в 59 %
случаев. Всё, что достаточно велико, чтобы его резать, стоит отправлять надёжно, и
вызов отправки говорит об этом прямо, а не даёт вызывающему обнаружить это в
продакшене.

## Потоки состояния владельца

Клиент, владеющий сущностью, сообщает о ней с частотой обновлений клиента.
Полезную нагрузку пишет собственный сериализатор типа сущности, поэтому тип,
определённый модом, передаётся без изменений протокола.

Обновления **сжимаются дельтой относительно снапшота, который клиент применил** и
который назван по идентификатору. Этот baseline — тот, что прислал сервер и
который он до сих пор держит в истории этого клиента, так что обе стороны называют
одну и ту же точку отсчёта.

Именно это делает дельта-сжатие безопасным на ненадёжном канале. Схема «дельта
относительно того, что я отправил в прошлый раз» молча рассинхронизируется в тот
момент, когда одно обновление потеряно: получатель применяет следующую дельту к
неверной основе и не имеет способа об этом узнать. Здесь потерянное обновление
стоит одного кадра свежести, а baseline, выпавший из истории, просто игнорируется,
и клиент перебазируется на следующий применённый снапшот.

## Адаптивная полоса

Бюджет снапшота каждого клиента следует за тем, что тянет его канал: срезается до
75 % при потерях выше 8 %, отползает обратно на 10 % от максимума за каждую чистую
секунду, с настраиваемым нижним пределом. Аддитивный рост, мультипликативное
падение — та же форма, что у TCP, и по той же причине.

Меняется только то, сколько отправляется за снапшот. Это никогда не меняет то, что
хранит сервер, и никогда не удаляет сущность навсегда: меньший бюджет откладывает
больше сущностей на будущие снапшоты, поэтому перегруженный клиент сходится
медленнее — но сходится.

## Временная шкала интерполяции

Удалённые игроки отрисовываются с фиксированной задержкой позади **оценки**
клиентом серверных часов, а не позади метки времени последнего снапшота.

Оценка продвигается каждый кадр и подталкивается к авторитетному значению при
приходе снапшота — постепенно при малых расхождениях и скачком при больших
(зависание или свежее подключение). Жёсткая коррекция на каждом снапшоте заставила
бы шкалу отрисовки прыгать вместе с сетевым джиттером, что выглядит как
подёргивание удалённых игроков.

Если же вести шкалу прямо от последнего снапшота, она станет лестницей 20 Гц, и
удалённый пед делал бы один шаг на снапшот независимо от того, как быстро
отрисовывается игра — что полностью обесценивает интерполяцию.
`SessionTests.RemotePlayersAreInterpolatedAtFrameRateNotAtSnapshotRate` измеряет
это напрямую: 16 различимых отрисованных позиций в секунду с лестницей и более 40
с оценёнными часами.

`InterpolationDelay` (по умолчанию 120 мс, примерно два интервала снапшота плюс
запас на джиттер) обменивает отзывчивость на плавность. Уменьшите — удалённые
игроки начнут дёргаться; увеличьте — они сильнее отстанут от своей реальной
позиции.

## Ресинхронизация

Клиент запрашивает ресинхронизацию, когда не может декодировать дельту:

- названный baseline выпал из его истории (долгое зависание);
- дельта пришла для сущности, отсутствующей в baseline;
- полезная нагрузка называет тип сущности, для которого в этой сборке нет
  сериализатора.

Сервер очищает состояние репликации этого клиента и присылает полный снапшот.
Сессия не разрывается — сбой декодирования восстановим, и считать его фатальным
означало бы превратить икоту в отключение.
