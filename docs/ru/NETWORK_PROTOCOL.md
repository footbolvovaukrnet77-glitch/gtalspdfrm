# Сетевой протокол

> Русская версия. English: [../NETWORK_PROTOCOL.md](../NETWORK_PROTOCOL.md).

Транспорт: UDP. Порядок байтов: little-endian. Версия протокола: **3**
(`ProtocolConstants.ProtocolVersion`); несовпадение отклоняется во время
рукопожатия с читаемым сообщением.

## Кадрирование пакетов

Каждая датаграмма начинается с магического числа `0x504D5447` (`"GTMP"`) и байта
вида. Магия — дешёвый фильтр, чтобы посторонний трафик отбрасывался до разбора.

### Без соединения (kind = 0)

Используется до существования сессии и только для рукопожатия.

```
u32      magic
u8       kind = 0
u8       messageType
varuint  length
bytes    payload
```

### Сессионный (kind = 1)

```
u32      magic
u8       kind = 1
u32      sessionId
u16      sequence        номер этого пакета; 1..65535, никогда не 0
u16      ack             наибольший номер пакета, полученный от собеседника, либо 0
u32      ackBits         битовое поле: бит i подтверждает (ack - 1 - i)
message* до конца датаграммы
```

Кадрирование сообщения внутри пакета:

```
u8       flags           бит0 = надёжное
u16      reliableSeq     присутствует только для надёжных
u8       messageType
varuint  length
bytes    payload
```

`MaxPacketSize` равен 1200 байт — достаточно мало, чтобы пережить наименьший MTU в
публичном интернете без IP-фрагментации. Одно сообщение может нести не более
`MaxPacketSize - 32` байт; всё, что больше, отклоняется на вызове отправки, а не
молча обрезается, и предполагается, что верхние слои сами делят свои полезные
нагрузки (кодировщик снапшотов так и делает).

## Надёжность

Подтверждение — **на уровне пакетов**. Каждый отправленный пакет запоминает, какие
идентификаторы надёжных сообщений он нёс; когда пакет подтверждён, все надёжные
сообщения внутри него списываются разом. Неподтверждённый пакет ставит в очередь
ровно свои собственные сообщения.

- **Тайм-аут перепосылки** использует оценщик Джекобсона/Карелса — тот же, что и
  TCP, — ограниченный диапазоном [50 мс, 1 с].
- **Упорядоченная доставка**: получатель буферизует надёжные сообщения,
  пришедшие не по порядку, и выдаёт их по порядку. Буфер ограничен 512 записями,
  чтобы враждебный собеседник не мог исчерпать память, придерживая один номер.
- **Подавление дубликатов**: надёжное сообщение с номером ниже отметки доставки
  отбрасывается. Поэтому перепосылки, пересекающиеся со своим подтверждением,
  бесплатны.
- **Учёт потерь**: пакет, выпавший из окна подтверждения в 32 пакета так и не
  будучи подтверждённым, засчитывается потерянным ровно один раз. Именно эту
  цифру показывает сетевой отладчик.

### Номер пакета 0 зарезервирован

Удалённый номер у собеседника начинается с нуля, поэтому его самому первому пакету
нечего подтверждать. Отправка `ack = 0` в этом пакете, при том что 0 — тоже
допустимый номер пакета, означает, что другая сторона прочтёт это как
подтверждение своего собственного первого пакета.

Это не косметика. Надёжные сообщения «подтверждённого» пакета списываются из
списка перепосылки и больше никогда не отправляются; а поскольку доставка
упорядочена, каждое последующее надёжное сообщение встаёт в очередь за номером,
который никогда не придёт, и канал заклинивает — молча, навсегда, до конца
соединения. Ситуация, которая это вызывает, совершенно обыденна: сервер ставит в
очередь уведомление о входе в тот момент, когда принимает клиента, ещё до того как
у клиента появится peer, чтобы его принять, а первое обновление состояния клиента
приносит обратно `ack = 0` до срабатывания таймера перепосылки.

Поэтому номера пакетов начинаются с 1 и пропускают 0 при переполнении, а `ack = 0`
означает «я от вас ещё ничего не получил» и не подтверждает ничего. Цена — один
бит подтверждения на каждые 65536 пакетов, что проявляется как одна лишняя
перепосылка.

Регрессионный тест:
`ReliabilityTests.AReliableMessageSentBeforeThePeerExistsIsStillDelivered`.

### Задержка подтверждения

Подтверждение ждёт до `NetPeer.MaxAckDelay` (20 мс) исходящего трафика, чтобы
поехать на нём попутчиком. Обе стороны обычно отправляют несколько раз в секунду,
поэтому подтверждения едут бесплатно; задержка порождает отдельный пакет только
когда собеседник иначе молчит.

Без этого собеседник, которому нечего отправлять, придерживает подтверждения до
секундного keep-alive, что раздувает измеренный RTT на порядок и задерживает
каждое решение о перепосылке. Это была реальная ошибка, пойманная тестом
`ReliabilityTests.RoundTripTimeIsEstimatedFromAcknowledgements`.

## Рукопожатие

```
КЛИЕНТ                                          СЕРВЕР
  │  ConnectRequest (без соединения)              │
  │  ─ версия протокола, версия клиента           │
  │  ─ имя игрока, токен личности, пароль         │
  │  ─ nonce клиента                              │
  │  ─ манифест модов + хеш схемы сущностей       │
  │ ────────────────────────────────────────────► │
  │                                               │ проверка версии
  │                                               │ проверка имени, пароля
  │                                               │ сравнение манифестов модов
  │                                               │ восстановление/создание игрока
  │  ConnectAccept (без соединения)               │
  │  ─ id сессии, id игрока, id сущности игрока   │
  │  ─ эхо nonce, частоты тика/снапшотов          │
  │  ─ время сервера, отчёт совместимости модов   │
  │ ◄──────────────────────────────────────────── │
  │                                               │
  │  ═════ дальше идут сессионные пакеты ═════    │
  │  ClientStateUpdate ──────────────────────────►│  30 Гц, ненадёжно
  │ ◄────────────────────────────────── Snapshot  │  20 Гц, ненадёжно
```

Запрос повторяется каждые 500 мс, до 20 попыток.

**Рукопожатие идемпотентно.** Accept — единственный пакет, за которым нет слоя
надёжности: он отправляется до того, как сессия существует. Если он потерян,
клиент повторяет запрос, и сервер обязан ответить на этот повтор, а не
маршрутизировать его в полуоткрытую сессию, созданную первым запросом. Повторный
запрос с тем же токеном личности и nonce получает байт-в-байт тот же accept
заново. Без этого клиент, чей accept потерялся, оказывается брошенным, пока не
сдастся; см. `SessionTests.ALostAcceptDoesNotStrandTheClient`.

Nonce также не даёт принять запоздавший accept от брошенной попытки за живую
сессию.

### ModEvent (`0x2A`)

```
string   name            маршрутизация по имени, а не по id в порядке регистрации
varuint  senderPlayerId  только сервер → клиент; 0 означает сам сервер
bytes    payload         непрозрачно; ни одна сторона его не интерпретирует
```

Маршрутизация по имени, а не по идентификатору, выданному в порядке регистрации,
сделана намеренно: два клиента, загрузившие свои моды в разном порядке, иначе
направляли бы события друг друга в неправильный обработчик; кроме того, это
снимает потолок на количество событий, которые мод может зарегистрировать.

`senderPlayerId` существует потому, что сервер может пересылать событие клиента
остальным игрокам (см. [MOD_SDK.md](MOD_SDK.md#пересылаемые-события)).
Пересланное событие, потерявшее источник, было бы бесполезно для чего угодно
персонального. На участке клиент → сервер поле игнорируется: отправитель — это
сессия, по которой пришёл пакет, а значение, присланное клиентом, ничего не стоит.

## Снапшоты

```
varuint  snapshotId          ненулевой, растущий для каждого клиента
varuint  baselineId          0 означает «полное состояние»
varuint  tick
f64      serverTime
u8       flags               бит0 = присутствует блок окружения
[environment]
varuint  removedCount
varuint  removedEntityId *
varuint  entityCount
  varuint  entityId
  u8       entryFlags        бит0 = полное состояние
  [u8      typeId]           только для полного состояния
  fields                     полное: все поля; дельта: varuint-маска + изменённые
```

Идентификаторы снапшотов — **на клиента**, а не глобальные: каждый клиент
подтверждает свой собственный поток, а сервер кодирует относительно того, что этот
клиент подтвердил последним.

### Почему базовые представления, а не один текущий мир

Дельту нужно декодировать ровно против того состояния, против которого она была
написана. Пока подтверждение летит, сервер продолжает кодировать против более
старого baseline, поэтому клиент не может просто применять дельты к одному
изменяемому миру — старый baseline должен всё ещё существовать.

Поэтому обе стороны хранят короткую историю неизменяемых `EntitySnapshotView` (по
умолчанию 64), и каждая дельта называет то представление, против которого была
написана. Применение дельты против неверного baseline **отвергается**, а не
делается на удачу: `SnapshotCodec.Apply` бросает исключение, и клиент запрашивает
ресинхронизацию.

Представления разделяют ссылки на сущности для всего, что не изменилось, поэтому
история глубиной 64 стоит одного словаря на снапшот, а не 64 глубоких копий
(`SnapshotTests.BaselineViewsShareUnchangedEntityInstances`).

### Байтовый бюджет

У каждого снапшота есть жёсткий байтовый бюджет (`snapshotByteBudget`, по
умолчанию 1024). Кодировщик обходит сущности в порядке приоритета и пишет то, что
помещается. Всё, что не поместилось, **откладывается на следующий снапшот**, а не
теряется — его baseline-состояние просто переносится у клиента дальше.

Это и есть механизм, позволяющий оптимизировать репликацию, ни разу не сокращая
состояние мира на сервере.
`StressTests.DistanceNeverRemovesAnEntityFromTheServerWorld` разбрасывает 100
сущностей по всей карте, далеко за любым радиусом стриминга единственного
подключённого игрока, и утверждает, что клиент сходится ко всем ним.

## Квантование

| Величина | Кодирование | Диапазон | Худшая ошибка |
| --- | --- | --- | --- |
| Ось позиции | zig-zag varint от `round(value × 512)` | ±16384 м (XY), ±2048 м (Z) | 0,98 мм |
| Ось скорости | zig-zag varint от `round(value × 128)` | ±256 м/с | 3,9 мм/с |
| Угол | `u16` от `градусы × 65536/360` | 0–360° | 0,0027° |
| Единичный скаляр | `u8` | 0–1 | 0,2 % |

Значения вне диапазона **ограничиваются, а не заворачиваются**: испорченная
координата даёт позицию на краю мира, которую ловит валидатор, а не позицию,
которая молча оказывается где-то правдоподобно.

Граница для позиции проверяется на 5000 случайных выборках в
`SerializationTests.QuantizedPositionStaysWithinTheDocumentedErrorBound`.

## Фрагментация

Надёжное сообщение, превышающее бюджет на сообщение, режется на фрагменты, каждый
из которых — обычное надёжное сообщение:

```
u16 groupId | u8 index | u8 count | u8 innerType | chunk
```

Порядок и перепосылка достаются бесплатно от надёжного канала, поэтому сборке не
нужна собственная схема подтверждений. Получатель буферизует фрагменты до полноты
набора, затем выдаёт собранное сообщение под его внутренним типом.

Пределы, оба — границы по памяти: 256 КБ на сообщение и 8 одновременных наборов
фрагментов. У собеседника, открывающего больше наборов, чем он завершает, самый
старый отбрасывается.

**Ненадёжная фрагментация не предлагается, а отклоняется.** Потеря любого одного
фрагмента теряет всё сообщение, поэтому эффективная частота потерь умножается на
число фрагментов: сообщение из 5 фрагментов на канале с 10 % потерь доходит в 59 %
случаев. Всё, что достаточно велико, чтобы его резать, стоит отправлять надёжно, и
вызов отправки говорит об этом прямо, а не даёт вызывающему обнаружить это в
продакшене.

## Потоки состояния владельца

Клиент, владеющий сущностью, сообщает о ней с частотой обновлений клиента.
Полезную нагрузку пишет собственный сериализатор типа сущности, поэтому тип,
определённый модом, передаётся без изменений протокола.

Обновления **сжимаются дельтой относительно снапшота, который клиент применил** и
который назван по идентификатору. Этот baseline — тот, что прислал сервер и
который он до сих пор держит в истории этого клиента, так что обе стороны называют
одну и ту же точку отсчёта.

Именно это делает дельта-сжатие безопасным на ненадёжном канале. Схема «дельта
относительно того, что я отправил в прошлый раз» молча рассинхронизируется в тот
момент, когда одно обновление потеряно: получатель применяет следующую дельту к
неверной основе и не имеет способа об этом узнать. Здесь потерянное обновление
стоит одного кадра свежести, а baseline, выпавший из истории, просто игнорируется,
и клиент перебазируется на следующий применённый снапшот.

## Адаптивная полоса

Бюджет снапшота каждого клиента следует за тем, что тянет его канал: срезается до
75 % при потерях выше 8 %, отползает обратно на 10 % от максимума за каждую чистую
секунду, с настраиваемым нижним пределом. Аддитивный рост, мультипликативное
падение — та же форма, что у TCP, и по той же причине.

Меняется только то, сколько отправляется за снапшот. Это никогда не меняет то, что
хранит сервер, и никогда не удаляет сущность навсегда: меньший бюджет откладывает
больше сущностей на будущие снапшоты, поэтому перегруженный клиент сходится
медленнее — но сходится.

## Временная шкала интерполяции

Удалённые игроки отрисовываются с фиксированной задержкой позади **оценки**
клиентом серверных часов, а не позади метки времени последнего снапшота.

Оценка продвигается каждый кадр и подталкивается к авторитетному значению при
приходе снапшота — постепенно при малых расхождениях и скачком при больших
(зависание или свежее подключение). Жёсткая коррекция на каждом снапшоте заставила
бы шкалу отрисовки прыгать вместе с сетевым джиттером, что выглядит как
подёргивание удалённых игроков.

Если же вести шкалу прямо от последнего снапшота, она станет лестницей 20 Гц, и
удалённый пед делал бы один шаг на снапшот независимо от того, как быстро
отрисовывается игра — что полностью обесценивает интерполяцию.
`SessionTests.RemotePlayersAreInterpolatedAtFrameRateNotAtSnapshotRate` измеряет
это напрямую: 16 различимых отрисованных позиций в секунду с лестницей и более 40
с оценёнными часами.

`InterpolationDelay` (по умолчанию 120 мс, примерно два интервала снапшота плюс
запас на джиттер) обменивает отзывчивость на плавность. Уменьшите — удалённые
игроки начнут дёргаться; увеличьте — они сильнее отстанут от своей реальной
позиции.

## Ресинхронизация

Клиент запрашивает ресинхронизацию, когда не может декодировать дельту:

- названный baseline выпал из его истории (долгое зависание);
- дельта пришла для сущности, отсутствующей в baseline;
- полезная нагрузка называет тип сущности, для которого в этой сборке нет
  сериализатора.

Сервер очищает состояние репликации этого клиента и присылает полный снапшот.
Сессия не разрывается — сбой декодирования восстановим, и считать его фатальным
означало бы превратить икоту в отключение.
