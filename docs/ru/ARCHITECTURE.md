## Проекты

| Проект | Целевая платформа | Зачем существует |
| --- | --- | --- |
| `Gtamp.Shared` | `netstandard2.0` | Всё, о чём обе стороны обязаны договориться: формат на проводе, модель сущностей, кодек снапшотов, состояние мира, правила античита, логирование. Цель netstandard выбрана так, чтобы клиент на .NET Framework и сервер на .NET 8 загружали *одну и ту же* сборку и не могли разойтись. |
| `Gtamp.Server` | `net8.0` | Авторитетный координатор. Кроссплатформенный, без зависимости от игры. |
| `Gtamp.Client.Core` | `netstandard2.0` | Вся логика клиента, не касающаяся GTA V. Тестируется без установленной игры. |
| `Gtamp.Client.Shv` | `net48` | Хост ScriptHookVDotNet. Намеренно тонкий — реализация моста, отрисовка консоли и насос тиков. |
| `Gtamp.Adapters.Rph` | `net48` | Опциональная интеграция с RAGE Plugin Hook, загружается только при наличии RPH. |
| `Gtamp.Adapters.Lspdfr` | `net48` | Опциональная интеграция с LSPDFR, то же правило. |
| `Gtamp.RphBridge` | `net48` | Вторая половина интеграции с RPH, загружаемая RAGE Plugin Hook, а не ScriptHookVDotNet. Это единственная сборка здесь, ссылающаяся на RPH, и ничто в клиенте не ссылается на неё. |
| `Gtamp.Tests` | `net8.0` | xUnit. Покрывает всё, кроме слоя-хоста ScriptHookVDotNet, которому нужна запущенная игра. xUnit гоняет тест-**классы параллельно** и создаёт новый экземпляр класса **на каждый тест**, поэтому класс может создавать и удалять только пути внутри собственного каталога — классы персистентности используют `gtamp-tests/<guid>/`. Удаление чего-либо общего, как бы аккуратно оно ни было обставлено проверками, гоняется с классами, работающими рядом, — и гонялось ровно столько, сколько проверка выглядела разумной. |

## Четыре шва

Проект держится на четырёх намеренных границах. Каждая существует, чтобы не
пускать целую категорию проблем в остальную систему.

### 1. `IGameBridge` — шов движка

Всё, что специфично для GTA V, находится за одним интерфейсом из двенадцати
членов. Выше него никто не знает, что такое `Ped`.

Именно это делает клиент тестируемым: `FakeGameBridge` в тестовом проекте
реализует его меньше чем в 60 строках, и полные тесты сессии — подключение,
репликация, движение, отключение, переподключение — выполняются вообще без
игрового процесса.

Это также означает, что второй хост (ScriptHookVDotNetCore или сборка под RPH) —
это новая реализация моста, а не форк.

### 2. `IDatagramTransport` — сетевой шов

`UdpDatagramTransport` для реальной работы; `LoopbackNetwork` для тестов, с
настраиваемыми задержкой, джиттером, потерями и переупорядочиванием, управляемыми
виртуальным временем.

Каждый сетевой тест — надёжная доставка при 40 % потерь, сходимость снапшотов при
байтовом бюджете, повтор рукопожатия при потерянном accept — выполняется
детерминированно за миллисекунды именно благодаря этому шву. Ни один из них не
спит.

### 3. `INetEntitySerializer` — шов расширяемости

Слой репликации разговаривает только с этим интерфейсом. Тип сущности,
зарегистрированный модом, неотличим от `PlayerEntity` для всех слоёв выше — именно
это делает утверждение «добавить тип сущности, не переписывая сетевой слой»
фактом, а не заявлением. Доказательство —
`ModSdkTests.AModDefinedEntityReplicatesThroughTheOrdinarySnapshotPath`.

### 4. `InProcessChannel` — шов между хостами плагинов

RAGE Plugin Hook и ScriptHookVDotNet — это два хоста .NET внутри одного процесса
GTA V, у каждого свой загрузчик и свой планировщик, и поддерживаемого пути между
ними нет. `Gtamp.Shared.Interop.InProcessChannel` и есть этот путь: две
ограниченные `ConcurrentQueue<byte[]>`, опубликованные через данные `AppDomain`,
несущие **байты под именем темы** и никогда — объекты.

Правило «только байты» — не осторожность, а необходимость: два хоста могут
загрузить разные копии одной и той же сборки, и тогда тип из одного не является
тем же типом для другого, а любой общий объект нельзя привести. Гарантированно
совпадают только типы фреймворка и байтовые раскладки.

Правило «не блокировать» — необходимость того же рода: работа RPH идёт на
`GameFiber`, а работа ядра — на потоке скриптов, поэтому блокирующий вызов из
любого в другой приводит к взаимной блокировке игры. Переполненная очередь
выбрасывает самое старое сообщение и считает его — потеряна свежесть, а не кадр.

`Gtamp.Client.Mods.BridgeLink` находится на стороне ядра и раздаёт сообщения по
темам, потому что `OpenCoreSide()` возвращает представление на одну пару очередей,
а не приватную, и два адаптера, вычитывающие её напрямую, крали бы сообщения друг
у друга.

## Поток данных

### Клиент → сервер (ввод)

```
Кадр игры
  → IGameBridge.SampleLocalPlayer()
  → ClientStateUpdateMessage          (ненадёжно, 30 Гц)
  → NetPeer                           упаковка, нумерация
  → UDP
  → GameServer.HandleClientStateUpdate
  → AntiCheatEngine.ValidatePlayerState
  → принято ? запись в PlayerEntity : отбросить (состояние сервера остаётся)
```

### Сервер → клиент (состояние)

```
Тик снапшота (20 Гц), для каждого клиента
  → ReplicationPriority.Order(...)    оценка по расстоянию и «залежалости»
  → SnapshotCodec.Write(world, baseline, budget)
  → NetPeer                           ненадёжно
  → UDP
  → ReplicatedWorld.TryApply          декодируется против названного baseline
  → RemotePlayerManager.Sync          в буферы интерполяции
  → ApplyServerCorrection             локальный игрок привязывается, если уплыл
  → RemotePlayerManager.Render        каждый кадр, на estimatedServerTime − задержка
```

### Надёжные события

Чат, события жизненного цикла сущностей, объявления сервера и события модов идут
через тот же `NetPeer` по надёжно-упорядоченному каналу: перепосылаются до
подтверждения, доставляются в порядке отправки, ровно один раз.

## Потоки

Сервер работает в одном тик-потоке плюс читатель stdin, который только кладёт
строки в очередь. Клиент работает целиком на потоке скриптов ScriptHookVDotNet.
Разделяемого изменяемого состояния между потоками нет, блокировок на горячем пути
нет.

`LogBus` — исключение: он защищён блокировкой, потому что приёмники добавляются из
одного потока, а запись идёт из другого, а запись в буфер обмена делегируется
короткоживущему STA-потоку.

Мост RPH — второе исключение, и это причина, по которой канал между ними — очередь,
а не вызов. Он работает на `GameFiber` от RPH, то есть на совершенно другом
планировщике; две стороны никогда не вызывают друг друга, они только кладут в
очередь и вычитывают.

Это осознанный выбор. Ошибки конкурентности в слое репликации воспроизводить
чрезвычайно трудно, а тик 60 Гц на несколько десятков игроков не нуждается в
параллелизме.

## Политика отказов

Три правила, применяемые повсеместно:

1. **Испорченный пакет никогда не фатален.** Каждый путь декодирования бросает
   `NetSerializationException`, который перехватывается на границе сообщения,
   логируется под `NETWORK`/`SECURITY`, а пакет отбрасывается. Тик-цикл
   продолжается.
2. **Отказавшая подсистема отключается, а не эскалируется.** Адаптер, бросивший
   исключение при обновлении, удаляется и логируется; клиент продолжает работать.
   Приёмник логов, бросивший исключение, игнорируется. Неудачная запись в
   хранилище логируется; мир остаётся живым.
3. **Невосстановимое декодирование — это ресинхронизация, а не отключение.** Если
   клиент не может декодировать дельту, он запрашивает полный снапшот, и сервер
   его присылает.

## Где живут инварианты

| Инвариант | Обеспечивается в |
| --- | --- |
| Сервер никогда не удаляет сущность из-за расстояния | `ServerWorld` — единственное место, где сущности добавляются и удаляются, и в нём вообще нет удаления, знающего о расстоянии |
| Расстояние влияет только на приоритет | `ReplicationPriority.Score` — единственное место, где читается расстояние |
| Дельта декодируется против того состояния, для которого написана | `SnapshotCodec.Apply` отвергает несовпадение baseline вместо применения |
| Идентификаторы сущностей не переиспользуются | `ServerWorld.AllocateEntityId` + `ReserveEntityIdsUpTo` после восстановления |
| Клиент никогда не источник истины | `GameServer.HandleClientStateUpdate` отбрасывает отвергнутые обновления |
| Типы модов не могут столкнуться со встроенными | `ModSdk.RegisterEntity` следит за зарезервированным диапазоном идентификаторов |
