# Mod SDK

> Русская версия. English: [../MOD_SDK.md](../MOD_SDK.md).

## Для чего он

Чтобы сторонний мод мог добавить сетевой тип сущности, событие, RPC, активность и
собственное состояние — не патча фреймворк и не меняя ни строки в сетевом слое.

## Соответствие разделу 21

Мастер-промпт перечисляет пятнадцать имён `Register*`. Вот чем каждое из них
является сегодня. С фазы 9 реализованы все; ничего в этой таблице не является
заглушкой, которая молча ничего не делает, и ничто больше не бросает «пока нет».

| Имя из промпта | Статус | Примечания |
| --- | --- | --- |
| `RegisterEntity()` | **Реализовано** | Регистрирует сетевой тип сущности; возвращает его id на проводе |
| `RegisterSerializer()` | **Реализовано** | Синоним `RegisterEntity` |
| `RegisterVehicle()` | **Реализовано** | `RegisterEntity` с читаемым именем в месте вызова |
| `RegisterPed()` | **Реализовано** | то же |
| `RegisterObject()` | **Реализовано** | то же |
| `RegisterComponent()` | **Реализовано как `RegisterState`** | Компоненты — это состояние с ключом-строкой на сущности |
| `RegisterState()` | **Реализовано** | Объявляет ключ `CustomData`, чтобы `/entity` мог его описать |
| `RegisterNetworkEvent()` | **Реализовано** | Маршрутизируется по имени через `ModEvent` (`0x2A`); о доставке другим клиентам см. [Пересылаемые события](#пересылаемые-события) |
| `RegisterOwner()` | **Реализовано как `NetEntity.OwnerId`** | Владение — это поле, а не регистрация |
| `RegisterDimension()` | **Реализовано** | Выделяет id измерения, чтобы два мода не столкнулись |
| `RegisterInterior()` | **Реализовано** | Именует id интерьера, чтобы он пережил перезапуск |
| `RegisterRPC()` | **Реализовано** | Регистрирует процедуру, которую другая сторона может вызвать и получить ответ |
| `RegisterMission()` | **Реализовано** | Регистрирует локальную половину активности: метки, маркеры, UI |
| `RegisterCustomWeapon()` | **Реализовано** | Даёт оружию имя локально; диапазон, против которого оно арбитрируется, регистрируется на сервере — см. [Кастомное оружие](#кастомное-оружие) |
| `RegisterDeserializer()` | **Не отдельный** | Сериализатор объявляет оба направления |

Пока член не был реализован, он бросал исключение с номером фазы, а не молчал, и
это было намеренно: регистрация, которая как будто удалась, а потом никогда не
срабатывает, отлаживается гораздо тяжелее, чем отказ при загрузке, называющий
причину. То же правило действует для всего, что добавится позже.

## Определение сущности

```csharp
public sealed class TurretEntity : NetEntity
{
    public TurretEntity(EntityId id) : base(id, (EntityType)128) { }

    public int Ammo { get; set; }
    public bool Deployed { get; set; }

    public override NetEntity Clone()
    {
        var clone = new TurretEntity(Id) { Ammo = Ammo, Deployed = Deployed };
        CopyBaseTo(clone);        // никогда не забывайте: копирует трансформацию и CustomData
        return clone;
    }
}
```

Регистрируйте её при инициализации адаптера, до любого соединения:

```csharp
public void Initialize(IModSdk sdk, ModEnvironment environment)
{
    sdk.RegisterMod(new ModDescriptor
    {
        Id = "my-mod",
        Name = "My Mod",
        Version = "1.0.0",
        Requirement = ModNetworkRequirement.Optional,
    });

    sdk.RegisterEntity(new TurretSerializer());
}
```

С этого момента `TurretEntity` реплицируется в точности как игрок: полное
состояние при первом появлении, дальше дельты, в порядке приоритета, с учётом
бюджета, сохраняется как непрозрачный блоб.

## Сетевые события

```csharp
sdk.RegisterNetworkEvent("turret.fire", (senderPlayerId, payload) =>
{
    // выполняется в тик-потоке клиента
});

sdk.SendNetworkEvent("turret.fire", payload, reliable: true);
```

События маршрутизируются **по имени**, а не по идентификатору, выданному в порядке
регистрации.

Это различие важно. Выдача идентификаторов в порядке регистрации означает, что
стороны согласны только пока регистрируют в одинаковом порядке — и мод, который
добавит одно событие на клиенте, молча перенумерует все последующие события только
на этой стороне, так что `turret.fire` начнёт приходить в обработчик
`turret.reload`. Имена стоят нескольких байт на событие и снимают и эту связность,
и потолок в шестнадцать событий.

Имена регистронезависимы, поэтому два мода не могут разойтись в написании.
Отправка незарегистрированного события бросает исключение, а не молча теряется.

### Куда попадает событие клиента

По умолчанию — **на сервер и не дальше**. `SendNetworkEvent` с клиента доходит до
серверного обработчика, зарегистрированного через
`IServerModSdk.RegisterNetworkEvent`, и там останавливается. Это правильное
умолчание: сервер может проверить, ограничить частоту или действовать по событию
собственным авторитетом.

### Пересылаемые события

У сервера, который ничего не знает о вашем моде, нет обработчика для регистрации,
а без него два клиента с одним и тем же модом вообще не могут разговаривать. Для
этого случая сервер может переслать событие дословно:

```csharp
// на стороне сервера
sdk.RegisterRelay("mymod.pursuit");
```

или, для оператора без серверного мода, по имени в `server.json`:

```json
"relayedModEvents": [ "lspdfr.event", "rph.event" ]
```

Сервер не разбирает полезную нагрузку и не может её проверить, поэтому
**пересланное событие не несёт никакого авторитета**. Это один клиент сообщает
что-то остальным, а сервер играет роль почтового ящика. Принимающий обработчик
получает идентификатор игрока-источника как `senderPlayerId` и `0`, когда событие
пришло от самого сервера.

Всё, за что моду нужно поручительство сервера — счёт, спавн, разрешение — должно
идти через серверный обработчик или RPC. Оператор, не желающий, чтобы клиенты
передавали друг другу непрозрачные байты, опустошает `relayedModEvents`; моды,
опирающиеся на пересылку, тогда перестают ходить между клиентами — это
задуманный эффект, а не неисправность.

## Удалённый вызов процедур

```csharp
// На сервере
serverSdk.RegisterRpc("bank.balance", (session, payload) => Encode(BalanceOf(session)));

// На клиенте
sdk.CallServerRpc("bank.balance", request, result =>
{
    if (!result.Success)
    {
        // result.Error говорит почему: нет обработчика, обработчик бросил
        // исключение, тайм-аут или соединение оборвалось
        return;
    }

    Show(Decode(result.Payload));
});
```

Работает в обе стороны: клиент регистрирует через `RegisterRPC`, а сервер вызывает
через `CallClientRpc`.

Вызовы **всегда завершаются** — ответом, ошибкой удалённого обработчика или
тайм-аутом. Вызов, который может висеть вечно, — это ошибка мода, проявляющаяся как
зависшая игра, поэтому тайм-аут не опционален, и каждый незавершённый вызов
немедленно провалится при обрыве соединения, а не будет оставлен дожидаться
тайм-аута.

Обработчики синхронны по замыслу. Обе стороны выполняют код модов в одном потоке —
поток скриптов игры и тик-поток сервера, — поэтому асинхронному обработчику
понадобился бы планировщик, которого нет, и он приглашал бы моды делать медленную
работу посреди кадра.

## Активности

Активность — это миссия, вызов, работа, гонка или что угодно ещё с задачами и
участниками. **Это сущность.** В этом весь замысел: она реплицируется, сохраняется
и появляется в инспекторе сущностей ровно тем же механизмом, что и машина, без
какой-либо специфичной для миссий сетевой логики.

Сервер объявляет и ведёт её:

```csharp
serverSdk.RegisterActivity(
    new ActivityDefinition("traffic-stop", "Traffic stop") { TimeLimitSeconds = 600 }
        .WithObjective(1, "Pull the vehicle over")
        .WithObjective(2, "Speak to the driver")
        .WithObjective(3, "Resolve the stop"));

ActivityEntity? stop = serverSdk.Activities.Start("traffic-stop", playerId, now);
serverSdk.Activities.SetObjectiveState(stop.Id, 1, ObjectiveState.Completed, now);
```

Задачи продвигаются по одной; активность завершается, когда все они разрешены,
когда истекает её лимит времени или когда так решает мод. Всё, что осталось
нерешённым, помечается как пропущенное, поэтому клиент, отрисовывающий список
задач, никогда не покажет живую задачу у завершённой активности.

Клиент реагирует:

```csharp
sdk.RegisterMission("traffic-stop", new MyCalloutHandler());
```

Обработчик управляется **сравнением реплицированного состояния**, а не потоком
событий. Клиент, пропустивший снапшот, всё равно окажется в правильном месте, а
подключившийся посреди активности узнает о ней так, будто она только началась.
Обработчик, бросивший исключение, логируется и изолируется; он не может уронить
сессию.

Сущности, привязанные к активности, уничтожаются вместе с ней, поэтому моду не
нужно вести собственный учёт своих подозреваемых и реквизита ради их уборки.

## Пользовательское состояние

```csharp
sdk.RegisterState("lspdfr.callout", "вызов, которому принадлежит эта сущность");
sdk.SetState(entity, "lspdfr.callout", "traffic-stop");
```

Запись необъявленного ключа бросает исключение. Объявление — это то, что позволяет
`/entity` описать значение, и то, что мешает двум модам тихо драться за один ключ.

Состояние, записанное так, реплицируется со следующей дельтой сущности и
сохраняется вместе с ней, в том числе на сервере, который никогда не слышал о
моде.

## Кастомное оружие

Бой арбитрируется на сервере, поэтому у оружия две половины, и авторитетна только
одна из них.

**Со стороны сервера — половина, которая решает.**

```csharp
serverSdk.RegisterWeapon(new WeaponProfile("WEAPON_MYMOD_RAILGUN", maxDamagePerHit: 400, maxRange: 1000f));
```

или, для оператора без серверного мода, в `server.json`:

```json
"customWeapons": [
  { "name": "WEAPON_MYMOD_RAILGUN", "maxDamagePerHit": 400, "maxRange": 1000, "melee": false }
]
```

Это **потолки валидации, а не значения урона**. Сколько урона наносит попадание,
решает игра; профиль ограничивает то, что клиенту позволено заявить.

**Со стороны клиента — половина, которая даёт имя.**

```csharp
sdk.RegisterCustomWeapon("WEAPON_MYMOD_RAILGUN", new WeaponProfile("WEAPON_MYMOD_RAILGUN", 400, 1000f));
```

Это сопоставляет хеш joaat обратно с именем, чтобы `/entity`, консоль и
баг-репорты показывали `WEAPON_MYMOD_RAILGUN`, а не `0x3F2A91C4`. Никакого
диапазона это не даёт и дать не может: клиент, который мог бы объявить потолок
урона своего оружия, объявил бы любой потолок, какой захочет. Это закреплено в
`ContentNegotiationTests.AClientCannotWidenTheEnvelopeItsOwnHitsAreCheckedAgainst`.

**Не зарегистрировать нигде — не фатально.** Оружие без профиля откатывается к
`defaultMaxDamagePerHit` (250) и `defaultMaxRange` (400 м) — это разрешающее
поведение, а не блокирующее: моднутое оружие работает сразу. Теряется точность в
обе стороны: моднутому тазеру позволено заявить 250 урона, а моднутой
дальнобойной винтовке её законные попадания отвергаются дальше 400 м.

## Контент мода, которого нет у другого игрока

Модели передаются хешами и разрешаются среди локально установленных ассетов,
поэтому игроку без вашего мода на транспорт создавать нечего. Этот случай
сообщается, а не замалчивается:

| Сущность | Что делает другой клиент |
| --- | --- |
| Транспорт, объект | Не показывается ничего. Другая машина хуже отсутствия, потому что выглядит правильно |
| Игрок | Используется тело по умолчанию, а запись помечается `substituted` |

Каждый неразрешимый хеш записывается один раз — создание повторяется каждый
кадр — и появляется в `/diagnostics`, `/mods` и баг-репорте. См.
[ENGINE_ANALYSIS.md](ENGINE_ANALYSIS.md), §4.4.

Ничто из этого ничего не устанавливает. Фреймворк не может поставлять ассеты и не
делает вид, что может; он превращает «машина друга невидима» из загадки в строку
текста.

## Уровни требований к моду

| Уровень | Значение | Эффект, когда у собеседника мода нет |
| --- | --- | --- |
| `ClientOnly` | Чисто локально (текстуры, графика) | Никогда не сравнивается |
| `Optional` | Реплицируется, но деградирует аккуратно | Сообщается, никогда не блокирует |
| `Required` | Нужен обеим сторонам, иначе сущности не декодируются | Блокирует подключение, когда включён `enforceRequiredMods` |

Отказать во входе может только `Required`. Отсутствие опционального мода даёт
запись в отчёте, которую игрок видит в `/diagnostics`, и сессия продолжается —
мастер-промпт явно требует, чтобы отсутствующий мод не рушил мир.

## Написание адаптера

```csharp
public sealed class MyAdapter : IModAdapter
{
    public string Id => "my-mod";
    public string DisplayName => "My Mod";

    // ОБЯЗАН читать только запись окружения. См. правило ниже.
    public bool IsAvailable(ModEnvironment e) => e.Mods.Exists(m => m.Id == "my-mod");

    public void Initialize(IModSdk sdk, ModEnvironment environment) { }
    public void Update(double now) { }
    public void Shutdown() { }
    public string DescribeStatus() => "ok";
}
```

Соберите его как `Gtamp.Adapters.<Name>.dll` и положите в
`GTA V/Gtamp/Adapters/`.

### Одно жёсткое правило

**Конструктор и `IsAvailable` не должны касаться ни одного типа из
адаптируемого мода.**

Сборки адаптеров загружаются до подтверждения присутствия мода. В .NET Framework
ссылка на отсутствующую сборку падает только тогда, когда JIT компилирует метод,
который её использует, — поэтому пока эти два члена чисты, адаптер для мода,
которого у вас нет, загружается безвредно и сообщает, что неактивен.

Именно это делает фразу «RAGE Plugin Hook опционален» фактом, а не заявлением.

### Изоляция отказов

- Адаптер, бросивший исключение в `Initialize`, логируется и пропускается;
  остальные всё равно загружаются.
- Адаптер, бросивший исключение в `Update`, выключается и удаляется; клиент
  продолжает работать.

Оба случая покрыты тестами. Сторонний адаптер не может уронить сессию.
